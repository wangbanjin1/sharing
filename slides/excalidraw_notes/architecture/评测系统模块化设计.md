# 电信网络意图提取 Agent · Eval Run 评测系统模块化设计

面向数据流输入为历史网元单据流与多轮口语对话的电信网络保障场景下的意图提取 Agent，给出 Eval Run 评测系统的模块化架构设计。系统按“**用例构建 → 流式执行与环境 → Hook 证据采集 → 判定与归因 → 闭环治理**”五个解耦层次组织，既支持沿时间轴逐会话的记忆生命周期中间点评测，也支持端到端意图提取闭环评测和问题归因。

---

## 一、总体模块化架构

Eval Run 评测系统划分为五个核心模块，各模块之间不直接依赖对方内部实现，而是通过三类本地文件（用例文件 `eval_cases.jsonl`、运行日志 `run_traces.jsonl`、评测结果 `summary.json` 与 `details.jsonl`）衔接解耦，避免评测脚本与被测 Agent 强绑定。

![[eval_run_overall_modules.drawio.svg]]

| 模块                                    | 核心职责                                                                 | 上游输入                                                | 下游输出                                                                   |
| :------------------------------------ | :------------------------------------------------------------------- | :-------------------------------------------------- | :--------------------------------------------------------------------- |
| **1. EvalCase（用例构建）**                 | 从真实网元单据反推用户画像，基于画像合成“单据 + 对话”混合流、埋入记忆与意图测试点并生成真值                     | 一部分真实网元单据（提取画像与空值分布）、业务规则库（白名单/套餐/资费）、离线迭代 Badcase  | 用例文件 `eval_cases.jsonl`（含每处埋入点的期望意图与期望记忆条目），按需划分 Dev / Eval / Held-out |
| **2. Harness & Environment（流式执行与环境）** | 编排三组对照实验，按时间轴连续流式灌入单据与对话；只要前面做了埋入，每个会话实时评测意图或记忆，必要时用检查点回滚做多 Trial 隔离 | `eval_cases.jsonl`、被测 Agent 与记忆系统、外部只读知识源（RAG / 套餐） | 实时驱动被测系统运行，并通过只读 Hook 输出全量过程事件                                         |
| **3. Evidence（Hook 证据采集）**            | 在记忆写入、检索、单轮对话与任务结束等节点挂载只读 Hook，不改动业务代码即可自动记录并保存各环节数据              | Harness 与被测模块触发的 Hook 回调事件                          | 结构化过程日志 `run_traces.jsonl`（记录模型版本、用例与第几次尝试）                    |
| **4. Evaluator（判定与归因）**               | 离线读取过程日志，并行执行记忆过程评测与端到端闭环评测，汇总核心指标并完成失败模块归因                          | `run_traces.jsonl`、`eval_cases.jsonl` 中的期望意图与期望记忆条目 | 汇总结果 `summary.json` 与逐条明细 `details.jsonl`（含失败归因标签）                     |
| **5. Governance（闭环治理）**               | 依据归因结果驱动算法优化与基准维护两条独立闭环，防止对调优集过拟合与评测漂移                               | `summary.json`、`details.jsonl`、人工抽检样本               | 更新后的用例集/评估器、迭代后的记忆与意图版本                                                |

### 1.1 模块解耦机制与三类中间文件

评测系统将记忆模块、意图提取模块与评测流水线均视为独立的功能模块，彼此不耦合内部实现，而是通过三类本地中间文件衔接，好处在于：
第一，更换被测模型、意图模块实现或对照组（如无记忆基线）时，评测主流程无需改动；
第二，调整打分规则、新增指标或更换 Judge 模型时，直接读取已保存的过程日志离线重算，无需重新消耗 Token 跑测试；
第三，记忆模块的底层存储方式（文件、SQLite 或向量库）调整时，不影响评测读取与判分逻辑。

为避免上述强绑定问题，评测链路通过三份结构清晰的中间文件解耦：

| 中间文件                                       | 衔接边界                   | 核心内容                                                                                                                                 | 隔离收益                                                                      |
| :----------------------------------------- | :--------------------- | :----------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------ |
| **用例文件（`eval_cases.jsonl`）**               | EvalCase → Harness     | `case_id`、用户画像、按时间排列的网元单据与对话混合流、各会话埋入的评测目标（记忆演进预期 / 意图期望模板 / 交互轮次上限）                                                                 | 任意模型、框架或对照组复用同一份数据                                                        |
| **过程日志（`run_traces.jsonl`）**               | Hook 采集 → Evaluator    | `run_id / case_id / trial_id`、模型与记忆配置版本、每次记忆写入前后的变更、每次检索的分库路由与 Top-K 列表、每轮对话全文、外部查询结果、最终意图产物、轮数/Token/时延                             | **判定层与执行层彻底解耦**：Evaluator 只读日志不碰被测 Agent；改指标、修判分 Bug 或换 Judge 模型均可离线零成本重算 |
| **评测结果（`summary.json` + `details.jsonl`）** | Evaluator → Governance | `summary.json` 存版本信息与分场景汇总指标（`EM`、`F1`、`MRR`、`pass@k`、`pass^k`、澄清减少率、Token 节省率及 `Oracle − Full` 差值）；`details.jsonl` 按用例记录子项得分与失败归因标签 | 看板展示、跨版本回归对比与 Badcase 筛选均只读结果文件，不受评测代码重构影响                                |

### 1.2 被测对象最小接入适配接口（Adapter）

在此解耦结构下，任何新的意图提取 Agent 或记忆系统接入本评测底座，只需提供一个轻量适配层（Adapter），对外暴露以下最小动作，无需改动评测编排与判分代码：
1. **`ingest_event(event)`**：按时间顺序接收流式网元单据或历史对话，驱动记忆模块提取、更新与演进。
2. **`step(user_message, context)`**：接收当前会话的单轮用户输入，执行记忆检索、外部只读查询（RAG/套餐）与意图决策，返回本轮回复（反问、咨询、拒识或最终意图模板）。
3. **`save_checkpoint() / restore_checkpoint(ckpt_id)`**：仅在多 Trial 独立重复采样或同一段历史挂载多道题时调用，用于将记忆库与会话状态回滚到指定检查点，防止跨 Trial 状态污染。
4. **生命周期 Hook 注册**：允许评测框架注册只读回调钩子（`on_memory_write`、`on_memory_retrieve`、`on_turn_end`、`on_task_finish`），线上不注册即零侵入。

## 二、模块一：EvalCase 用例构建

EvalCase 负责明确“用什么测、埋入哪些评测点、期望结果是什么”，内部按“画像提取 → 混合流合成 → 治理划分”三步展开：

### 2.1 真实单据反推画像与双源混合流合成
- **第一步（真实单据提取画像）**：抽取一部分真实网元单据，提取真实用户画像（主力应用、规律作息、基础套餐、常见保障参数区间）以及真实空值（`null`）与异常单据分布，避免拍脑袋虚构脱离业务的场景。
- **第二步（基于画像合成单据 + 对话混合流）**：以提取出的用户画像为起点，沿时间轴往后合成持续流式的网元单据与稀疏多轮口语对话，按需埋入长期习惯形成、偏好冲突更新、临时切换与到期恢复、可控噪声（短时取消单据、卡顿异常记录、同期无关并行单据）以及位置粒度隔离等演化事件。
- **场景显式区分**：将评测会话明确划分为**无需记忆场景**（检验记忆系统不引入误干扰）与**需用记忆场景**（检验记忆系统带来的准确率与交互效率增益）。

### 2.2 意图与交互覆盖
- **核心任务边界**：覆盖网络保障诉求（输出应用/子业务、起止时长算术一致、体验参数归一化三要素模板）、假设性咨询与业务/资费/白名单规则咨询、**域内规则驳回**（白名单/时间/参数/套餐 MOS 越界与情绪反语拦截），以及**域外与闲聊快速收口**（问候自然、越界不代答、1~2 轮温和拉回或收口，跑题不丢槽位且闲聊不入库）。
- **语言与参数复杂度**：覆盖间接语用暗示、信息缺失或指代模糊（`Underspecified`）、多业务并发防混淆、否定排除防误抽（如“只保腾讯会议，抖音不用保”）、复杂句法与参数错误。
- **多轮交互边界**：定义快路径直接闭环、带澄清的慢路径闭环、多轮动态收敛（澄清中途反问规则、中途改口清旧约束、长会话保留关键字段原值）与执行恢复，明确最大澄清轮次上限 \(X\)。

### 2.3 用例治理与数据集划分
- **真值确定性校验**：结合确定性业务规则校验时间算术一致性（如 `end - start == duration`）与槽位合法性，生成每处埋入点对应的期望意图模板与期望记忆条目。
- **防泄露审核**：审核题目描述清晰可解，剔除在用户提问话术中直接暴露标准答案线索的样本；迭代中发现的离线 Badcase 经去歧义后补充进用例库。
- **数据集划分（参考机器学习与 Agent 评测通用惯例，如 Anthropic Evals 实践）**：为避免调 Prompt 和记忆规则时对评测集过拟合，按用途划分为 **Dev 调优集**（日常开发调试）、**Eval 回归集**（版本合入横向对比）与 **Held-out 盲测集**（仅里程碑验收，严禁参与调优）；项目冷启动初期样本量较小时，可先合并为 **Dev + Held-out** 两集，后续再拆出独立回归集。

## 三、模块二：Harness 与 Environment（连续流式执行与检查点隔离）

Harness 与 Environment 负责按真实时间轴驱动流式数据与多轮对话，同时通过对照实验与检查点机制保证结果可复现、可归因。

![[eval_harness_stage_a_b.drawio.svg]]

### 3.1 Evaluation Harness 编排控制器
- **多维交叉评测（`Model × Harness × Task`）**：不只评估单一模型分数，支持把“底层模型 × 记忆/工程组件 × 任务集”做受控交叉实验，明确收益来自底层模型还是记忆与工程框架。
- **三组受控对照（对应 `E1`）**：在同一份 `eval_cases.jsonl` 上平行运行三组配置，用于剥离上游记忆误差与下游意图误差：
  1. **无记忆基线（`No-Mem`）**：关闭长期记忆，衡量纯意图提取下界与无需记忆场景基线；
  2. **真实记忆（`Full-Mem`）**：完整接入被测记忆系统，衡量流式记忆沉淀、检索与意图理解联调的真实表现；
  3. **标准记忆上界（`Oracle-Mem`）**：在评测会话直接注入该时间点的期望记忆条目，剥离上游记忆写入与检索误差，测算下游意图理解与决策模块的能力上界。
- **阶段记忆积累对照（对应 `E4`）**：在“阶段 1 结束”与“全部历史结束”两个时间点分别冻结记忆检查点，保持模型、Prompt、工具、规则与交互预算完全一致，仅改变记忆积累条件，在同一批未参与学习的**留出新任务**上对比测试（涵盖跨阶段信息组合、个性化规则形成、局部规则修订、程序经验迁移，以及未改规则与不适用经验反例），测算留出任务净增益 \(\Delta \text{EM}\)。
- **预算与重复采样控制（对应 `E2`）**：对每个会话统一限定最大澄清轮次 \(X\)、工具调用步数与超时熔断，在多轮澄清、冲突更新、边界拒识等高波动题上独立重复运行 \(k\) 次 Trial（如 \(k=3\)），评估 `pass^k`（稳定下限）、`pass@k`（能力上限）与基线波动区间。

### 3.2 连续流式回放与按埋入点实时评测
- **业务主链路不割裂**：单据与对话按时间戳顺序连续流式输入。遇到历史单据或前序对话时，直接流经记忆模块完成抽取、习惯归纳、冲突置旧（`superseded`）或受控遗忘；推进到任意用户会话时，自然就能查到前面所有会话和单据已经沉淀下来的记忆。
- **每个会话按埋入实时触发评测**：不局限于时间轴末尾的单个测试点，只要前面做了埋入（无论是记忆演化埋点还是意图理解埋点），系统都会在对应会话实时触发意图闭环评测或记忆读写/检索评测；该会话结束后，新产生的信息继续留存并流向后续会话。
- **外部只读源与模拟用户**：每个会话中，被测 Agent 可查询只读的外部知识库 RAG（业务、资费、白名单）与用户套餐档位（最低 MOS 与 VIP 优先级），并与持有隐含真实需求的 User Simulator 开展 1 至 \(X\) 轮动态对话（模拟补参、冲突确认、改口或撤销）。

### 3.3 检查点（Checkpoint）回滚隔离与多会话 `pass@k` / `pass^k` 推进策略
连续流式执行本身不需要硬拆成两个孤立阶段，但在以下两种工程场景下，Harness 会在进入评测会话前自动保存一次记忆库检查点（Checkpoint），并在每次采样结束后回滚复原：
1. **避免重复跑历史建库**：当同一道题需要重复运行 \(k\) 次独立采样（计算 `pass@k` / `pass^k`），或同一段多周历史后面挂载了多道不同测试题时，如果每次都从第 1 天重头流式灌入单据与对话，会导致大量重复的 LLM 写入调用，成本高且耗时长；
2. **防止跨 Trial 状态污染**：第 1 次采样的对话过程可能向记忆库写入新的临时记录或经验条目，若不回滚到进入该会话前的检查点，第 2 次采样就会受到第 1 次采样的残留状态干扰，导致采样不再独立。

此外，在多会话连续流式场景下，当前会话重复尝试 \(k\) 次会产生 \(k\) 份不同的记忆演化结果，而后续会话又依赖当前会话沉淀的新记忆。为兼顾稳定性评测与跨会话误差隔离，按阶段采用两种推进策略：
- **日常迭代（Dev / Eval）：局部多采样 + 标准对话轨迹推进**。在当前埋点会话开始前保存检查点，先基于真实动态对话（Agent ↔ 模拟用户）独立跑 \(k\) 次计算该会话的 `pass@k` / `pass^k`；随后回滚到该检查点，将用例预设的标准对话轨迹喂给**被测记忆模块**正常走一遍写入（记忆状态仍完全由记忆模块自行提取演进，不硬塞真值），再带着这份干净状态继续推进至下一会话，防止单次随机失误引发后续整条故事线雪崩。
- **里程碑验收（Held-out 盲测）：整条故事线端到端独立跑 \(k\) 遍**。对代表性长程故事线不切分检查点，从初始状态到最终会话全程动态跑 \(k\) 遍，真实检验跨会话记忆写入误差累积下的端到端长程稳定性。

## 四、模块三与模块四：Hook 证据采集与 Evaluator 双线判分

为了避免仅看最终答案掩盖中间过程缺陷（例如记忆检索漏召回却靠模型猜对，或冗余追问拉低体验），系统在不改动原有业务代码的前提下，通过只读 Hook 自动记录并保存各环节的运行数据，再在离线判分侧拆分为**记忆生命周期评测**与**记忆内容及意图闭环评测**两条主线。

![[eval_evidence_and_evaluator.drawio.svg]]

### 4.1 基于 Hook 的过程数据采集
评测框架在四个关键节点挂载只读 Hook，不影响被测模块的正常返回值，统一按 `run_id / case_id / trial_id` 写入 `run_traces.jsonl`：
1. **`on_memory_write`**：每次单据或对话流经记忆模块时触发，记录写入前后状态变更、抽取条目与版本置旧记录（支撑 `M1 / M2`）。
2. **`on_memory_retrieve`**：每次意图模块查询记忆时触发，记录分库路由结果与检索返回的 Top-K 候选列表及排序分数（支撑 `M3`）。
3. **`on_turn_end`**：每轮对话结束触发，记录直通或澄清路由决策、**实际调用的外部资源库清单**（RAG / 套餐 / 记忆库，支撑 `F3` 资源路由与无关库免查率）、追问与改口全文、本轮 Token 消耗与**首轮/单轮响应时延**。
4. **`on_task_finish`**：会话结束触发，记录最终输出的意图模板或咨询/拒识判定、累计对话轮数、用户主动补充槽位字段数、总时延及**会话终止原因**（正常闭环 / 超轮次 / 中途退出，支撑 `E3`）。

### 4.2 Evaluator 双线判分引擎（4 模块 13 项最小必测体系）
Evaluator 离线读取 `run_traces.jsonl`，不依赖被测 Agent 在线运行，按四类 13 项核心维度展开判分：
- **一、记忆生命周期（过程白盒，`M1 ~ M3`）**
  - **`M1` 记忆形成（提取）**：正向核验单据与对话的事件、稳定偏好（\(\ge N_{\min}\)，权重上“对话+单据 > 单次对话 > 单次单据”）及个性化表达抽取；负向监控将假设咨询、闲聊、偶发或被动降质单据误写入导致的幻觉误写入率与有效信息遗漏率。
  - **`M2` 记忆演进（更新）**：正向核验显式变更即时生效、临时配置到期回退与按场景分域更新；负向监控旧偏好残留率、临时偏移误覆盖率与未改场景偏好保持率。
  - **`M3` 记忆检索**：正向核验 `Recall@K`、`Precision@K`、`nDCG@K`、`MRR`，以及**已入库条件 `Recall@K` 与入库覆盖率**（无 Ground Truth 证据的样本记 `N/A`）；负向监控无关记忆误引入率（`FRR`）与负干扰致错率（`NIR`）。
- **二、长期记忆功能（内容落地，`F1 ~ F3`）**
  - **`F1` 情景记忆**：覆盖时间指代与平移、业务/子应用指代、历史场所指代、运行质量与状态指代 4 类跨会话回溯，监控无效事件/无关单据误召率。
  - **`F2` 语义记忆**：覆盖个性化表达映射、按场景隔离存储与应用、周期偏好临时调整后还原与已知免重问，监控跨场景误套用、无记录直接猜测与旧偏好覆盖本次明确参数。
  - **`F3` 程序记忆**：覆盖①资源按需路由（无关库免查率）、②澄清与冲突复用（如时段重叠或节假日冲突给出“顺延/暂停”闭合选项）、③场景避错经验迁移（如大型场馆预热在新场馆泛化）；负向监控禁用边界误套用率与错误经验重放率。
- **三、意图闭环（`I1 ~ I3`）**
  - **`I1` 要素抽取与复杂句法**：清晰/口语/复杂句法转三要素标准模板、多业务并发防混淆、否定排除防误抽。
  - **`I2` 语用边界与快慢路由**：间接语用理解、假设性咨询防误执行（仅咨询误触发执行率）、快路径直接闭环、带澄清的慢路径闭环及外部客观事实优先查只读信息核验。
  - **`I3` 违规驳回、域外与多轮收敛**：域内规则驳回、域外与闲聊快速收口（目标平均 1~2 轮、越界不代答、闲聊不入库）、缺失槽位定位（追问槽位 F1）、改口旧约束残留率与长会话关键字段原值保留率。
- **四、端到端整体效能（`E1 ~ E4`）**
  - **`E1` 受控对照与三层归因**：统计 `No-Mem / Full-Mem / Oracle-Mem` 的 `EM`、净提升 \(\Delta \text{EM}\)（允许为负）、上游记忆损耗（`Oracle − Full`）及三层失败归因分布。
  - **`E2` 多采样运行稳定性**：统计高波动题重复 \(k\) 次的 `pass^k`、`pass@k` 与基线波动区间。
  - **`E3` 交互效率与系统开销**：统计 `ΔTurns`（**仅在配对均成功样本上计算**，避免将失败提前退出误算成效率高）、全量失败率/超轮次率/中途退出率、用户需主动补充槽位字段数、累计 Token 节省率（`ΔTokens`）、首轮与端到端总时延。
  - **`E4` 记忆积累后的留出新任务增益**：统计留出新任务净增益 \(\Delta \text{EM}\)（百分点），配套约束未受影响旧能力保持率、记忆使用边界违规率与交互效率。

### 4.3 混合判定器、关键红线与结果输出
- **确定性规则断言与一票否决红线**：三要素意图模板采用全字段精确匹配（`EM`）加时间算术校验；**未澄清直接执行（`PER`）触发时，即使模型蒙对参数仍判 `EM = 0`**，配合冗余追问率（`OCR`）与澄清决策 F1 共同约束快慢路径边界。
- **轨迹级 Judge 为辅**：针对间接语用、多轮消歧提问质量、域外温和收口与改口响应贴合度等非结构化维度，结合规则约束与 LLM Judge 判分，并定期人工抽检校准评估器一致性。
- **结果输出**：汇总指标写入 `summary.json`（含无需记忆 / 需用记忆分开统计与 `E1~E4` 效能指标）；逐条用例的得分、红线触发记录与三层失败归因写入 `details.jsonl`。

## 五、模块五：Governance 持续治理与闭环迭代

评测运行结束后，依托三组对照分数拆解误差来源，将 `details.jsonl` 中的失败样本分流至**算法优化**与**基准维护**两条独立闭环。

![[eval_governance_attribution_loop.drawio.svg]]

### 5.1 基于对照差值的三层失败归因
结合 `Oracle-Mem − Full-Mem`（上游记忆损耗）、`100% − Oracle-Mem`（下游意图损耗）以及 `run_traces.jsonl` 中的过程记录，将失败样本按链路精确归因至三层：
1. **未入库（写入与演进层，`M1 / M2`）**：目标信息未被提取写入，或冲突更新时未停用旧值、被临时偏移误覆盖（对应入库覆盖率缺口）。
2. **已入库未召回（检索层，`M3`）**：目标记忆已在库中，但检索未命中、排序靠后，或被无关记忆（`FRR`）挤占（对应已入库条件 `Recall@K` 缺口）。
3. **已召回未正确应用（意图与决策层，`F1~F3 / I1~I3`）**：目标记忆已召回（或在 `Oracle-Mem` 下已直接注入），但仍出现句法理解偏差、时间算术错误、未澄清直接执行（`PER`）、边界误套用或负干扰致错（`NIR`）。
4. **评测自身异常分流**：若复核轨迹发现用例本身存在二义性、模拟用户偏离画像约束或 Judge 误判，则归入基准异常，不计入算法退化。

### 5.2 双闭环落地机制
- **闭环 A（算法优化闭环）**：将上游记忆损耗定向反馈至记忆写入、状态更新与混合检索引擎；将下游意图损耗反馈至意图提取 Prompt、澄清策略与经验记忆沉淀（高频确定性规则下沉为硬固化校验，复杂交互策略沉淀为软固化经验条目），改完后重测验证净收益。
- **闭环 B（基准维护闭环）**：持续清理用例歧义、修正模拟用户提示词、校准评估器一致性，并将离线迭代中暴露的典型失败样本补充进用例库；全程保持 Held-out 盲测集独立，确保长期评测结论客观可信。
