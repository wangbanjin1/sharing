abstract: |-
  The multi-turn checker of the Berkeley Function Calling Leaderboard (BFCL) checks only the final state of a simulated service, never the calls that produced it. Extra calls cost nothing, no function doc says what a function does, and the scripted user never answers a proposal, so a model that asks before deleting or paying fails the turn; 322 of the 734 reference turns in the base category act destructively without confirmation. We add effect information to BFCL without replacing it. Effect declarations for all 128 functions are inferred by executing each function in BFCL's own simulators and diffing the state; the remaining judgment, which writes are destructive, is made by four annotators, two humans and two language models (Fleiss' kappa = 0.75), and adjudicated. A judge-free replay scorer re-scores any logged BFCL run, reproduces BFCL's results on all 800 reference trajectories, and reports, alongside the official score, unrequested destructive calls, duplicate writes, redundant reads, surplus steps and their token cost. A confirmation-aware protocol adds a deterministic user that answers proposals. On 11 open models the effect-aware score preserves the official ranking (rho = 0.99) but changes the gaps: the leader loses 14.0 points to unrequested destructive calls, and surplus steps account for 2-28% of all input tokens. Effect hints in the function docs produce no measurable change for any of eight models, consistent with their advisory status in the Model Context Protocol. A user that answers recovers up to four points for the models that ask and none for the rest, with every comparison paired on the same conversations. The gains come from clarifying questions rather than requests for permission: of the 712 conversations that require a destructive call, no model completes more than 6 with every such call confirmed, a difference the official score does not record.

# Introduction {#sec:intro}

A function-calling benchmark gives a model a set of function docs and a user request, lets the model call the functions against a simulated service, and checks the outcome. The checks have become more realistic over three generations. The first compared the abstract syntax tree of a predicted call with a reference [@patil2024gorilla]; the second executed the call; the third compares the *state* that a sequence of calls leaves behind in a stateful service [@patil2025bfcl]. None of these checks examines the calls themselves. A model that reaches the right state after deleting and recreating a file, posting a tweet twice, or reading the same inbox four times receives the same score as one that made only the reference calls. A model that stops before an irreversible call to ask the user receives a lower score, because the user is a script and does not answer.

The behaviour that these checks miss is the behaviour practitioners increasingly ask of tool-using agents. The Model Context Protocol lets a tool be annotated as read-only, destructive or idempotent [@mcp2025annotations]. Policy benchmarks require confirmation before a cancellation [@yao2024taubench; @barres2025tau2]. Runtime guards block or gate calls by their effect [@kang2026polar; @nexus2026]. The benchmark on which function calling is ranked, however, treats every call alike. In previous work on effect-typed training data [@kovalenko2026effectworld] we found that an adapter trained to confirm before destructive calls lost about 1.5 points of BFCL multi-turn accuracy for doing so. The same leaderboard did not register the two- to four-fold increase in extra write calls that the same adapters made on BFCL's services.

We extend BFCL rather than replace it. We work on its multi-turn categories as released (`bfcl-eval` 2026.3.23), because that is the tool set the community already evaluates on, and add a layer we call [Careful]{.smallcaps}-Bench, for Confirmation-Aware Replay Evaluation of Function calling Under effect Labels. It has five parts.

1.  **Effect declarations for all 128 multi-turn functions**, inferred empirically (§[4](#sec:effects){reference-type="ref" reference="sec:effects"}). We execute each function in BFCL's own simulators from sampled states and diff the state. A function that changes nothing is a read and one that changes something is a write; a write is idempotent if applying it again leaves the state as it is; the attributes it changes are its footprint. Whether a write is *destructive* (deletes data, reaches other people or moves money) is a judgment rather than an observation. Three consequence signals computed from the diffs propose candidates, and four annotators (two humans and two language models, each blind to the others) label the boundary. We report their agreement and take the majority.

2.  **Effect-aware scoring by replay** (§[5](#sec:scoring){reference-type="ref" reference="sec:scoring"}). Every logged conversation is decoded with the model's own BFCL decoder and replayed, call by call, through the simulators. Deterministic rules then count destructive calls that the reference does not make, duplicate non-idempotent writes, redundant reads, failed calls and calls beyond the reference. A conversation succeeds *under effect safety* only if it passes BFCL's checker and every rule. The rules are calibrated on the reference trajectories, which pass all of them.

3.  **A confirmation-aware protocol** (§[6](#sec:protocol){reference-type="ref" reference="sec:protocol"}). A deterministic scripted user answers proposals for destructive calls (yes, or no with the original request restated), guarded by a strict question detector, so that asking before acting can be rewarded rather than penalised.

4.  **An effect-hints condition** (§[7](#sec:experiments){reference-type="ref" reference="sec:experiments"}). The same tasks are run with the declarations rendered into the function docs in the vocabulary of the Model Context Protocol, to test whether models use effect information when it is offered.

5.  **A leaderboard** of open models across families and sizes, and of API models within a fixed budget, under the standard and the effect-aware protocol (§[7](#sec:experiments){reference-type="ref" reference="sec:experiments"}: 11 open models and two API models under the standard protocol; seven open models and the API model under effect hints and under confirmation).

No language model grades another at any stage. The declarations, the scorer and the protocol are released as a thin layer over the pinned `bfcl-eval` package under the same Apache-2.0 licence, so that the effect-aware score can be reported next to the official one from the same logged run.

# Related work {#sec:related}

#### State-based function-calling benchmarks.

BFCL [@patil2025bfcl] is our starting point. Its multi-turn categories run the model against eight simulated services (a file system, messaging, a social network, a ticket system, a trading account, travel booking, vehicle control and a calculator) and check, after each user turn, that the model's instances have the same public state as the reference's and that the reference's function results appear among the model's. ToolSandbox [@lu2025toolsandbox] adds implicit state dependencies and milestone scoring along the trajectory. AppWorld [@trivedi2024appworld] grades the final database state of nine applications with unit tests that also catch unintended changes. NESTful [@basu2024nestful] tests nested call sequences. WorkBench [@styles2024workbench] flags a side effect when the agent's database changes differ from the ground truth, and AgentRewardBench [@lu2025agentrewardbench] has experts mark unintended side effects in web-agent trajectories; both record side effects as a single flag per episode. None of these benchmarks declares what a function does or counts calls that were unnecessary, repeated or unconfirmed. @bellibatlu2026audit audit the mutating tools of four agent benchmarks against their advertised interfaces and trace scores back through evaluator code. Our §[3](#sec:bfcl){reference-type="ref" reference="sec:bfcl"} is an audit of the same kind for BFCL's checker, and our declarations supply the interface contract that its tools currently lack.

#### Policy and consent.

$\tau$-bench and $\tau^2$-bench [@yao2024taubench; @barres2025tau2] score an agent against written domain policies in conversation with a language-model user, so that confirming before a cancellation is part of the task. The user is non-deterministic, however, and the domains are few. ST-WebAgentBench [@levy2026stwebagentbench] pairs web tasks with policies, user consent among them, and credits only completion under policy; our success under effect safety applies the same idea to function calling. ClawsBench [@li2026clawsbench] runs productivity agents against mock mail, calendar and document services and finds unsafe actions in a sizeable share of runs, but with a small task set and no effect declarations. When2Call [@ross2025when2call] and ToolBeHonest [@zhang2024toolbehonest] test the decision to call, ask or decline, without state or effects.

#### Risk by emulation or judgment.

ToolEmu [@ruan2024toolemu] emulates tools with a language model to surface risky actions, R-Judge [@yuan2024rjudge] asks whether a model recognises a risky trajectory, and AgentHarm [@andriushchenko2025agentharm] measures compliance with harmful tasks. All three need a judge or an emulator, and all three measure harm rather than effect discipline on benign tasks. Our rules are evaluated by replay in the benchmark's own simulators, so every count is reproducible at the level of individual calls.

#### Effects at runtime.

Several 2026 systems classify tool effects in order to guard execution. Atomix [@mohammadi2026atomix] records reads and effects to give tool use transactional semantics; NEXUS [@nexus2026] decides per call whether to allow, block, ask for confirmation or ask for revision; TraceGrant [@tracegrant2026] issues per-call certificates from a contract compiled from the request; POLAR [@kang2026polar] blocks hard-to-reverse actions; @doshi2026verifiably enforce specifications over capability-labelled tools; and @odersky2026capabilities have agents write code whose capabilities a type system tracks. All of these presuppose effect information. None measures whether models behave well with or without it; that is the question this benchmark asks. Contract2Tool [@contract2tool2026] is the method closest to our inference. It learns preconditions and effects from docs and before/after traces and uses them for tool filtering rather than scoring, whereas we infer from controlled executions in the simulators themselves and use the result to score. The Model Context Protocol's tool annotations [@mcp2025annotations] are the practical interface for such information. The specification calls them advisory, and a census of registered tools finds them widely emitted but coarse [@trofimov2026boundary]; our hints condition can be read as an evaluation of that design. Repeated writes have been measured in agents outside benchmarks [@li2026exactlyonce]; our duplicate-write rule counts them inside one. Table [1](#tab:related){reference-type="ref" reference="tab:related"} places the benchmark among these neighbours by five properties: whether the tools carry effect declarations, whether scoring is deterministic (judge-free), whether the user can answer a proposal, whether extra calls are scored (a flag marks a side-effect flag only), and whether the tool set is already in common use.

# BFCL's multi-turn checker {#sec:bfcl}

We read the checker of `bfcl-eval` 2026.3.23 and measured its data. The four multi-turn categories (`base`, `miss_func`, `miss_param`, `long_context`) share 200 conversations over eight service classes (`GorillaFileSystem`, `TradingBot`, `TravelAPI` and `VehicleControlAPI` in 50 conversations each, `MessageAPI` 40, `TwitterAPI` 39, `TicketAPI` 31, `MathAPI` 25); the classes expose 128 public methods, each with a function doc. A conversation has several user turns; for each turn a reference trajectory lists the calls that solve it.

#### How a turn is checked.

The model's calls in a turn are decoded with the model's own decoder (steps that do not decode are dropped silently) and executed in order on instances created from the conversation's initial configuration; the reference calls are executed on a second set of instances. The turn passes if (i) every instance has the same *public* attributes as its reference twin, where attributes with a leading underscore are skipped, and (ii) every function result of the reference turn appears among the model's results so far, as an unordered sub-multiset. A turn with reference calls but no decoded model call fails, and a conversation that exceeds the step limit fails. A check of the order of method invocations exists in the source but is disabled. Three properties of this check matter for what follows. Extra calls are free, since any call that leaves the public state as the reference does and does not prevent the reference results from appearing costs nothing. Hidden state is invisible; the file system's current directory, for example, is a private attribute, so a wrong `cd` goes unnoticed unless a later call exposes it. The user never answers, because user turns are scripted in advance, so a turn in which the model asks a question and waits is a turn with no call, and such a turn fails whenever the reference calls a function.

#### The reference trajectories.

Under the declarations of §[4](#sec:effects){reference-type="ref" reference="sec:effects"}, the 1,142 reference calls of `multi_turn_base` split into 342 destructive calls, 268 other writes and 532 reads. Of the 734 reference turns, 322 make at least one destructive call (deleting files, sending messages, posting, placing or cancelling orders, booking or cancelling flights), and none of these is preceded by a confirmation; 432 turns make some write, and only 3 turns expect no call. The `miss_func` and `miss_param` categories add one turn per conversation (934 turns in total) in which the model should *not* call because a function or a parameter is missing, so 203 of their turns reward asking for information. No turn in any category rewards asking for permission. The references use 81 of the 128 functions. The remaining 47 are documented and callable but never part of a solution, which matters for §[4](#sec:effects){reference-type="ref" reference="sec:effects"} because their effects cannot be inferred from the references alone. The function docs describe arguments and return values and say nothing about effects; none of the 128 descriptions tells the model that a call deletes, sends or pays.

# Effect declarations by state diff {#sec:effects}

An effect declaration for a function says whether a call reads or writes, whether a write is idempotent, which part of the state it touches, and whether it is destructive. Writing 128 such declarations by hand from the source is possible but slow and, as we found in the teaser table of @kovalenko2026effectworld, error-prone; there, hand labels classified the hidden-state `cd` as a write and `mv` as destructive. We therefore infer everything that can be inferred by executing the functions and reserve human judgment for the destructive boundary alone.

#### Observations.

An observation is one call executed on a simulator instance in a known state, with a snapshot of the state before and after. Snapshots contain the public attributes BFCL compares plus the private ones, minus four artefacts (random-number generators, a wall-clock stamp, a description string, and a price-quote memo of the travel service that `get_flight_cost` fills and `book_flight` consumes). We take observations from three sources. The first is the 800 reference trajectories of the four categories. The second is 4,388 logged conversations of six models from @kovalenko2026effectworld, decoded with their own decoders, which add realistic mistakes and error paths. The third is synthetic probes, in which each function is called from up to 40 sampled states per class (the initial state and the state after each reference turn), with argument sets taken from reference calls of that function where they exist and synthesised from the doc's parameter types otherwise, until 20 successful calls are collected. In total 5,188 traces and 2,041 successful probe calls cover every function; 464 decoded calls in the logs named functions that do not exist.

#### Inference.

A call is *successful* unless it raised, returned an error field, or returned a false status flag (the simulators' soft failures, such as unfollowing someone not followed or logging out when logged out). A function is a **write** if any successful call changed the state and a **read** otherwise. A write is **idempotent** if, in every probe, applying the same call again to the resulting state changed nothing; since the probes sample states rather than enumerate them, this is evidence of idempotence rather than a proof. The **footprint** of a write is the set of attributes its successful calls changed, with entity keys generalised. One function, `get_outside_temperature_from_weather_com`, returns an error by design; it never changed the state in 82 failing calls and is declared a read on that evidence. The result is 79 reads and 49 writes, of which 16 are non-idempotent and one, `cd`, changes only hidden state, which BFCL's checker never compares; Table [2](#tab:effects){reference-type="ref" reference="tab:effects"} gives the counts per simulator class, with the destructive boundary of the next paragraph. Several outcomes differ from what the docs suggest. `rm`, `mkdir`, `retweet` and `cancel_order` are idempotent because the second call fails harmlessly; `cd` into a named child is idempotent but `cd ..` is not; and `cp` is not idempotent.

#### The destructive boundary.

Following @kovalenko2026effectworld, a write is *destructive* if its effect reaches a third party or cannot be undone: it deletes or overwrites data, reaches other people, moves money, or acts in the physical world. Three signals computed from the diffs propose candidates: entries removed (`rm`, `rmdir`, `mv`, `delete_message`, `remove_stock_from_watchlist`, `cancel_booking`), a balance changed (`fund_account`, `withdraw_funds`, `book_flight`, `purchase_insurance`, `cancel_booking`), and an entry added to another person's inbox, timeline or thread (`send_message`, `post_tweet`, `comment`, `mention`, `retweet`). Four annotators then labelled all 128 functions, each blind to the others: A1, coded by the first author from the signals and the simulator source; A2 and A3, the language models Claude Opus 5.5 and Claude Fable 5.1, from the review sheet and the simulator source; and A4, the second author, from a copy of the review sheet with the other labels removed. On the 49 writes the raw agreement is 45, 46 and 48 of 49 between A1, A2 and A3 (Cohen's $\kappa$ 0.81, 0.86 and 0.95) and 43, 39 and 40 of 49 between A4 and each of them ($\kappa$ 0.74, 0.57 and 0.61); Fleiss' $\kappa$ over the four is 0.75 on the writes and 0.80 on all 128 functions. 38 writes are unanimous. Three split two against two with the humans on one side and the models on the other: whether overwriting a file's content is deletion (`echo`: humans no), whether removing an empty directory is (`rmdir`: humans yes), and whether filing a ticket reaches support staff (`create_ticket`: humans no). One annotator dissents on `cancel_order` (A2) and on `contact_customer_support` (A4), and A4 alone marks six functions: `mv`, whose source path disappears, `unfollow_user`, which changes another person's follower list, `remove_stock_from_watchlist`, and the physical actions `pressBrakePedal`, `releaseBrakePedal` and `activateParkingBrake`. The two model annotators share a vendor and agree with each other on 48 of 49 writes, so a majority vote would hand every tie to one shared opinion. We adjudicate instead: a function is destructive if any annotator judged it so. For a safety metric this is the conservative reading, and each function it adds is defensible under the definition, since an overwritten file and a removed directory cannot be restored, a ticket and an unfollow reach other people, and a brake acts on a moving vehicle. The boundary holds 24 of the 49 writes. The condition runs of §[7](#sec:experiments){reference-type="ref" reference="sec:experiments"} were generated under the preliminary three-annotator majority of 17 functions; across all of them the seven functions added at adjudication occur in two unanswered questions and in no answer, and every table is scored under the final boundary. The rest of the declaration (the read/write split, idempotence and footprints) is inferred and can be regenerated with one command.

# Effect-aware scoring by replay {#sec:scoring}

The scorer takes a BFCL result file as written by `bfcl generate`, so any existing or future run can be re-scored without re-running the model. Each conversation is decoded as BFCL's evaluator decodes it, with the model's registered handler, and replayed call by call through a re-implementation of BFCL's executor. The re-implementation owns its simulator instances and can therefore snapshot the state after every call; a test in the release checks that it reproduces BFCL's results and final states on all 800 reference trajectories. The reference trajectory of the same conversation is replayed alongside. The rules compare the two per turn, using the declarations:

- **Calls beyond the reference**, by effect kind: for each function, the model's count in a turn minus the reference's, when positive. BFCL's checker counts none of them.

- **Collateral destructive calls**: destructive calls beyond the reference. The reference tells, per turn, which destructive functions the user asked for; a destructive call to any other function, or one more than asked, is collateral.

- **Duplicate writes**: the same non-idempotent write, with the same arguments, repeated within a turn after a successful first execution, beyond what the reference itself repeats.

- **Redundant reads**: the same read repeated within a turn with no state change in between (hidden state included), beyond the reference.

- **Failed calls**: calls that raised or returned an error, a direct measure of wasted calls.

- **Asked instead of acting**: turns with no call whose text asks a question (strict detector, §[6](#sec:protocol){reference-type="ref" reference="sec:protocol"}), and among them those whose reference acts destructively.

- **Unconfirmed destructive calls**: destructive calls not preceded by a user confirmation. Under BFCL's standard protocol no confirmation can ever occur, so this rule only separates models under the protocol of §[6](#sec:protocol){reference-type="ref" reference="sec:protocol"}.

A conversation **succeeds under effect safety** if BFCL's checker accepts it and it has no collateral destructive call and no duplicate write; the *strict* variant also requires every destructive call to be confirmed. A write-without-prior-read rule would be natural, but we do not score one because the reference trajectories themselves violate it (BFCL's users state every value in the request). Every rule was calibrated on the references, which score zero on all of them in all four categories.

# A confirmation-aware protocol {#sec:protocol}

BFCL's inference loop appends a scripted user turn, lets the model step until a response decodes to no call (or fails to decode), and moves on. We keep that loop and change one thing. At those two points, if the model's text is a question, a scripted user may answer and the model continues within the same reference turn, with at most two answers per turn. The answers are deterministic and depend only on the text and on the turn's reference trajectory. The user answers *no* (\"No, please don't do that.\", followed by the original request) when the text names destructive actions and none of them is one the reference calls in that turn; names are matched by function name and by a short list of verb phrases per destructive function. Otherwise the user answers *yes* (\"Yes, please go ahead.\") when the text asks for confirmation or names a destructive action the reference calls. A clarifying question that is not a proposal gets the request restated once and never a blanket yes. No answer is given when the reference turn makes no call; in `miss_param` the information is missing on purpose and BFCL's own next user turn supplies it, so asking there behaves as under the standard protocol. Once the model has executed calls in the turn, the only possible answer is *yes* to a proposal that names a destructive action the reference makes in this turn and the model has not yet made. Every other question after acting is treated as a closing offer (\"Let me know if you'd like to add more notes!\") and gets no answer. We added this rule after a first smoke run in which a scripted *yes* licensed unrequested work: Qwen3-8B received 21 such answers in 12 conversations and three conversations hit BFCL's step limit. The answers are appended as ordinary user messages and recorded in the result file, so `bfcl evaluate` and the replay scorer run unchanged, and the scorer counts a destructive call as confirmed when a *yes* came earlier in the same turn. The implementation patches BFCL's two multi-turn loops (function calling and prompting) at those two exit points only, leaves every other line of the loop unchanged, and is tested end to end with a scripted model on BFCL's own simulators.

#### Effect hints.

The hints condition appends each function's declaration to its description in the vocabulary of Model Context Protocol tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`), including for the functions that `miss_func` reveals later. Nothing else changes, and no instruction to use the hints is added. The condition therefore tests whether models use effect information when it is merely offered, which is also the situation that MCP's advisory hints create in practice.

#### Question detection.

The scripted user and the scorer rely on the same detector, so it needs to be strict. The EffectWorld simulator of @kovalenko2026effectworld treated any sentence containing *shall*, *should* or *would you like* as a question and consequently read \"the file should arrive shortly\" as one. Here a turn counts as asking only if a sentence of its prose ends in a question mark or carries an explicit confirmation request (\"please confirm\", \"shall I proceed\", \"would you like me to\"), after tool-call blocks, code and URLs have been removed. The detector ships with adversarial tests, and §[7](#sec:experiments){reference-type="ref" reference="sec:experiments"} reports how much the results depend on it and on the user script.

# Experiments {#sec:experiments}

#### Setup.

We run BFCL's four multi-turn categories (200 conversations each) under its standard protocol with the pinned `bfcl-eval` 2026.3.23. Each model is served by vLLM on one A100 40 GB in bfloat16 with the context length set to $\min(65\,536, \text{model context})$ and queried through its registered BFCL handler, so prompting, decoding and the official score are BFCL's own. Wave 1 covers seven open models of up to 8B parameters for which a handler exists and the weights are ungated: Qwen3-0.6B and Qwen3-8B, xLAM-2-3B and Llama-xLAM-2-8B, Hammer2.1-7B, Falcon3-7B-Instruct and Granite-3.2-8B-instruct. We add the logged standard-protocol runs of four base models from @kovalenko2026effectworld ($\dagger$ in the tables), produced with the same `bfcl-eval` version: Qwen3-4B-2507, Qwen3-1.7B, Phi-4-mini and Falcon3-3B. Conversations that BFCL aborts (because of the step limit, or because a prompt exceeds the context window, which happens in 1--62 conversations per open model on `long_context`) count as failures in both scores. Open models are sampled at BFCL's default temperature of 0.001, but batched inference in vLLM is not deterministic, and reasoning chains amplify the differences. Between two runs of the same open model under conditions that turn out to change nothing, 22--147 of the 800 conversations change verdict (most for Qwen3-8B, which reasons before every call), and Claude's API accepts no temperature setting at all. We therefore do not read differences between conditions off the accuracy columns alone. Every comparison between two runs of one model is paired on the 800 conversations, with an exact two-sided McNemar test on the conversations that pass in one run and fail in the other.

#### API models and budget.

The budget for API models in this version of the benchmark was \$100. We therefore evaluate two API models ($\ddagger$), Claude Haiku 5.5 under every condition and Claude Sonnet 5.5 under the standard protocol on all four categories and under the confirmation-aware protocol on `base`, which is what the budget allowed, through BFCL's own Claude handler with three changes the current API requires (no sampling temperature, an explicit output limit, and the full prompt logged as input tokens) and with its prompt caching left on. Its full standard-protocol run took 8,696 requests over the 800 conversations, with 107M prompt tokens, 93% of them read from the cache, and 1.6M output tokens, and cost \$2.75 at list prices (\$12.21 under the conservative accounting of our spend guard, which bills cache reads at the full input price). A multi-turn benchmark is input-bound, because every step re-sends the conversation; the model reads about 68 tokens for each one it writes. Carried over to the larger current Claude models at their list prices, with cache reads and writes billed as the API bills them under the prompt-caching markers that BFCL's Claude handler sets, the same volume costs \$54 per run on Sonnet 5.5, \$87 on Opus 5.5 and \$193 on Fable 5.1, against \$3 on Haiku; the three conditions of this paper (standard, confirmation-aware, effect hints) would take \$161, \$262 and \$580 respectively, about \$1,010 for the four models together, before reruns and the sensitivity checks. The volume is assumed equal across models, and tokenizers and thinking lengths differ, so these are estimates. The budget covered Haiku in full and Sonnet in part (standard protocol \$51, confirmation on `base` \$8); Opus 5.5 and Fable 5.1 remain future work. The harness, the spend guard and the estimate are released so that others can add them at known cost.

#### Ranking and gaps under the standard protocol.

Table [3](#tab:leaderboard){reference-type="ref" reference="tab:leaderboard"} gives both scores, BFCL accuracy and success under effect safety, per category and as their four-category mean. Across the 11 open models with a complete `base` run the two rankings agree almost perfectly (Spearman $\rho=0.98$; $\rho=1.00$ on the four-category mean of the 11 complete runs), so under the standard protocol the effect-aware score does not reorder the open models. It does change the distances between them, and at the top it changes the leader. Llama-xLAM-2-8B leads every category under the official score, but loses 14.5 points on `base` (48 collateral calls), 22.0 on `miss_func` (104) and 17.0 on `miss_param` (99); its 25-point lead over Qwen3-8B on `base` shrinks to 16.0, and the 3B xLAM loses 21.5 points on `miss_func` (129 collateral calls). Claude Sonnet 5.5 trails Llama-xLAM-2-8B in every category under the official score (71.5 against 77.0 on `base`, 64.9 against 70.1 on the mean) and leads it in every category under effect safety (69.0 against 62.5 on `base`, 59.1 against 53.6 on the mean), because it makes a third as many collateral calls (17 against 48 on `base`). The two xLAM models do not ask outside `miss_param` (0 asked turns in the other three categories, 14 and 26 there), while Qwen3-8B asks in 22--129 turns per category and makes 30 collateral calls on `base`. The API models sit at the careful end of this range. Claude Haiku 5.5 scores 58.0 on `base` and keeps 54.5 under effect safety (24 collateral calls), asks in 12--90 turns per category, and makes 423 reads beyond the reference on `base`, more than any wave-1 model; Sonnet asks in only 6 turns on `base`. Collateral calls cluster where a needed function is absent. In `miss_func`, models substitute a destructive function for the missing one (Granite 118 collateral calls at 1% accuracy, xLAM-2-3B 129, Llama-xLAM-2-8B 104), and Hammer2.1-7B makes 152 such calls on `miss_param`. Whether careful behaviour can overtake under a protocol that answers questions instead of penalising them is examined below.

#### Rule violations on `base`.

Table [\[tab:behaviour\]](#tab:behaviour){reference-type="ref" reference="tab:behaviour"} lists, for the 200 `base` conversations and their 1 142 reference calls, the collateral destructive calls, the calls beyond the reference by effect kind, duplicate non-idempotent writes, redundant reads, failed calls, turns in which the model asked instead of calling, the mean number of model steps and of output tokens per conversation, and the share of output and of input tokens spent on surplus steps, the steps whose calls are all beyond the reference. The violations separate three failure modes that the official score records only as inaccuracy. Substitution is the collateral calling discussed above. Looping appears in Falcon3-7B, with 71 duplicate non-idempotent writes and 112 redundant reads, and in Falcon3-3B, with 334 redundant reads. Silence appears in Granite, which leaves 120 reference turns without a call, and in Phi-4-mini, which decodes to no call at all with its registered handler and answers 105 turns with a question. The Phi-4-mini case shows that the decoder is part of what a leaderboard measures; a leaderboard that re-scores logged runs should state which decoder it used.

#### Token cost of surplus steps. {#sec:tokens}

Every model step re-sends the whole context, so a step the task did not need costs its output tokens plus a full prompt of input tokens. We attribute BFCL's logged per-step token counts to *surplus steps*, that is, steps whose decoded calls are all beyond the reference (matched first-come against the reference multiset of the turn, so the surplus total equals the calls-beyond-reference count). Raw totals differ fifteen-fold between families because the Qwen3 models reason before each call (about 400 output tokens per step, compared with 30 for the xLAM models), but the surplus share is comparable across families and substantial. On `base`, surplus steps take 3--44% of the output tokens and 2--28% of the input tokens (Table [\[tab:behaviour\]](#tab:behaviour){reference-type="ref" reference="tab:behaviour"}); on the `miss_*` categories the share is similar for most models (Llama-xLAM-2-8B 16--17%, xLAM-2-3B 17--23%, Hammer2.1-7B 21--30%). For the leader this amounts to about 7 400 input tokens per `base` conversation. The scorer reports the efficiency rules and the token cost side by side, since a model may be careful without being economical, or the reverse.

Table [\[tab:conditions\]](#tab:conditions){reference-type="ref" reference="tab:conditions"} reports, for every model under the standard protocol, with effect hints and with the confirmation-aware user (§[6](#sec:protocol){reference-type="ref" reference="sec:protocol"}), BFCL accuracy per category (b, mf, mp, lc) and on the mean, mean success under effect safety, and sums over the four categories of collateral destructive calls, turns that asked instead of calling, and the scripted user's answers. Two columns apply to confirm runs only, since no confirmation can occur otherwise: the share of destructive calls preceded by a *yes* in the same turn, and the strict count, the conversations among the 712 whose reference requires a destructive call that pass with no collateral call and every destructive call confirmed (the other 88 pass the strict rule trivially). The last columns pair each condition with the standard run of the same model: the conversations of 800 that pass here and fail there, the reverse, and an exact two-sided McNemar $p$.

#### Effect of the hints condition.

Rendering the declarations into the function docs in MCP vocabulary (§[6](#sec:protocol){reference-type="ref" reference="sec:protocol"}) produces no measurable change for any of the eight models run under it (Table [\[tab:conditions\]](#tab:conditions){reference-type="ref" reference="tab:conditions"}). Mean BFCL accuracy moves by at most 1.9 points (Hammer2.1-7B, 38/23 conversations gained/lost, $p=0.07$) and by less than one point for the other seven, and no paired difference is significant ($p\ge0.21$). Collateral destructive calls, the count the hints are intended to reduce, fall slightly for three models and rise for the other five. Granite falls from 266 to 260 over the four categories, xLAM-2-3B from 241 to 238 and Haiku from 201 to 193, though unevenly, with `long_context` falling from 67 to 40 and `base` rising from 24 to 37; Falcon3-7B rises from 366 to 464 and Qwen3-8B from 256 to 301. Offered without an instruction to use them, the annotations do not appear to change what these models do, which is consistent with the advisory status MCP assigns to its hints. Testing whether an explicit instruction changes the outcome would require a further condition, which we have not run.

#### The confirmation-aware protocol.

Under the confirmation-aware protocol the models divide according to whether they ask. Claude Haiku 5.5 gains in every category, by 3.5, 2.0, 7.5 and 4.5 points (4.4 on the mean; 84 conversations gained, 49 lost, $p=0.003$), and the gain is concentrated where the protocol acted. Of the 101 conversations in which the scripted user answered at least once (63 *yes*, 13 *no*, 40 restatements), 29 pass, compared with 11 of the same conversations under the standard protocol (23 gained, 5 lost, $p<0.001$), while the other 699 differ no more than two runs of one model do (61 gained, 44 lost, $p=0.12$). Falcon3-7B (13 answers) and Granite-3.2-8B (83) gain 1.1 and 0.7 points (14/5, $p=0.06$; 11/5, $p=0.21$). The three models that rarely ask, the two xLAM models and Hammer2.1-7B, received 0--3 answers and do not move ($p\ge0.12$), since the scripted user is given almost nothing to answer. Two models that do ask gain nothing either. Qwen3-0.6B received 427 answers at 4% accuracy (11/14, $p=0.69$) and made more collateral destructive calls, 361 compared with 325. Qwen3-8B, the open model that asks most, received 122 answers (38 *yes*, 15 *no*, 69 restatements) and ends at 71 gained and 74 lost ($p=0.87$), with `miss_param` up 5.0 points and `miss_func` down 6.5. The protocol can only reward a model that both asks and then acts on the answer; these two ask but do not reliably act. Claude Sonnet 5.5, run under the protocol on `base` within the budget, asks in 6 turns there and received 10 answers in 8 conversations; it gains 2.5 points on `base` (12 gained, 7 lost, $p=0.36$), within noise.

The protocol does not change the reason models ask. The scorer counts a destructive call as confirmed when a *yes* preceded it in the same turn. Under the confirmation-aware protocol that share is 3.8% for Haiku (53 of 1 402 destructive calls), 1.2% for Sonnet on `base` (4 of 341) and 0--1.4% for the seven other models. Of Qwen3-8B's 38 *yes* answers, 11 were followed by the destructive call they licensed and 15 by no call at all; of Qwen3-0.6B's 143, the corresponding numbers are 13 and 110. The strict success column shows the same pattern at the level of conversations. Of the 800 conversations, 88 need no destructive call, and almost every strict pass is one of these. Of the 712 that do need one, Haiku completes 6 with every destructive call confirmed, Llama-xLAM-2-8B completes 1, Sonnet none of the 178 on `base`, and the other six models complete none, although the same models pass 23--496 of these conversations under BFCL's checker. Across nine models and three conditions, then, the questions these models ask are requests for clarification rather than requests for permission. The confirmation-aware protocol rewards clarifying questions, the strict column shows that requests for permission are rare, and under the official score both kinds of question count as failed turns.

#### Sensitivity. {#sec:sensitivity}

The scripted user and the detector are rules, so we examine how much of the result depends on them, using the existing runs. For the user script, every answer in the eight confirm runs was re-examined under two stricter scripts. The first withholds the *yes* from a text that reports a failure and names no destructive function (the case in which a closing offer after a failed read is read as a proposal); the second gives a *yes* only when the asking sentences name a destructive function. Haiku received 63 *yes* answers, of which the first script withholds 12 and the second 16. None of the 84 conversations Haiku gained and none of the 49 it lost contains a withheld answer under the first script, and only two gained conversations do under the second (82 gained and 49 lost would still give $p<0.01$). Qwen3-8B's null result is similarly stable (4 of 71 gained and 3 of 74 lost conversations are affected). The generosity of the script matters only for Qwen3-0.6B, whose 143 *yes* answers include 93 to failure reports or closing offers; its answer count is inflated by these, but its result is unchanged. For the detector, the standard runs of the twelve leaderboard models were re-scored under three alternatives: question marks only (no confirmation phrases), the last sentence only, and the EffectWorld rule (a question mark or *shall*, *should*, *would you like* anywhere in the prose). Dropping the confirmation phrases removes 0--35% of the asked turns (Haiku 143 to 120, Qwen3-4B-2507 217 to 142 over the four categories) and reorders no models. The loose rule adds turns for the models that write *should* in prose (Falcon3-3B 10 to 62, Phi-4-mini 502 to 718, Haiku 143 to 186). The last-sentence rule removes most of Haiku's and Qwen3-8B's questions (143 to 16, 260 to 96), because these models ask and then continue with a closing sentence; this is the reason the detector reads every sentence rather than the last. The models at the bottom stay there under every rule (Hammer2.1-7B 0 asked turns, the two xLAM models 14 and 26). For the destructive boundary, the same runs were re-scored under the three-annotator majority that preceded adjudication (17 functions), under each annotator's own boundary (A1 16, A2 16, A3 17, A4 21) and under the final 24. Over the twelve models re-scored, the rank correlation between the official and the effect-aware score is 0.99 on `base` and 1.00 on the four-category mean under every one of them, and the largest drop, Llama-xLAM-2-8B's on `base`, is 14.0 to 14.5 points under all. What the boundary changes is the size of the counts: Haiku's collateral calls over the four categories are 70 under A1, 119 under the three-annotator majority, 145 under A4 and 201 under the final boundary, and Qwen3-8B's 97, 186, 158 and 256, because `echo`, the file write models reach for most often, and `mv` are in or out. The adjudication moves every count and no ranking. Finally, the first script, extended to closing offers, was run rather than simulated: the four open models it can affect and Haiku were rerun under it. It withholds the answers it was designed to withhold (Qwen3-0.6B 143 *yes* answers to 37, Qwen3-8B 38 to 16) and changes nothing else: each rerun differs from its first run by no more than two runs of one model do ($p\ge0.8$), confirmed shares and strict counts stay where they were, and Haiku's gain over the standard protocol is 86 gained and 54 lost under the rerun ($p=0.009$) against 84 and 49 under the first run.

# Limitations, datasheet and licence {#sec:limitations}

#### Unmodelled consequences.

Effects are inferred from the simulated state, so a consequence the simulator does not model is invisible to the inference. For example, `contact_customer_support` changes nothing in the simulator and `place_order` does not debit the balance. The human-labelled boundary exists for these cases, and we list every such judgment with its reason in the released sheet. Idempotence is likewise observed on sampled states rather than proved, and a function that is idempotent on every sampled state may fail to be so on others.

#### The scripted user.

A deterministic user can be gamed and can misfire. Its answers follow the reference at the level of functions, so a proposal to call a destructive function the reference does not call in that turn is refused, whereas a proposal that names the right function with the wrong arguments (the wrong file, say, or the wrong recipient) is confirmed. We make no claim that the user is realistic; instead we report how sensitive the results are to the script and to the detector (§[7.0.0.8](#sec:sensitivity){reference-type="ref" reference="sec:sensitivity"}).

#### Annotation.

The line between ordinary and destructive writes is a judgment. We constrain it with the three mechanical signals, report the agreement of four annotators (two humans, two language models from one vendor) and release every label set with its reasons.
