## 一、核心思路与四大算法贡献

### 1. 一句话核心思路 (Core Insight)

传统工具评测（如初代 τ-bench、BFCL）默认所有状态都在云端后台，Agent 自己查库改库就能闭环；但真实的电信/运维排障是**视野隔离且动作耦合的双端博弈**——Agent 看得见后台账单与套餐限额，看不见用户手机是否误开飞行模式或省流限速；且后台改完配置（如开通漫游、下发催缴单）必须引导用户在手机端配合操作（开漫游开关、付款、重启测速）才能生效。

**τ²-Bench 的核心破局思路是将“双端协同排障”拆解为三套确定性工程机制**：

1. **运行时交互**：用“半双工控制权交接 + `sync_tools` 跨库状态钩子 + 视角翻转（`flip_roles`）”驱动 Agent 与用户模拟器各自调工具改状态；
2. **任务集构造**：摒弃人工编剧本，用“原子故障三元组 + 互斥选择集笛卡尔积 + 逐步必要性断言校验”程序化合成 100% 可解且每步必做的复合故障题；
3. **瓶颈归因**：用 `Default` vs. `No-User`（单人全控）vs. `Oracle Plan`（给标准剧本）三联消融，定量切分出“排障推理短板”与“引导用户操作短板”。

### 2. 四大核心贡献 (Key Contributions)

1. **双端协同（Dual-Control）交互沙箱**：将环境物理隔离为后台库 `Agent DB` 与终端库 `User DB`，双方仅能调用各自专属工具读写本端状态，底层通过同步钩子实时传导跨端因果效应（如后台充值成功自动解除终端断网限速）。
2. **零捷径的组合式程序化任务生成器**：将单一故障封装为绑定「注入—修复—断言」三函数的原子模块，按互斥选择集求笛卡尔积并通过**三步确定性自动验证**，零人工编写合成 **2,285 道**复合排障任务（分层采样 114 道评测）。
3. **工具锚定的低幻觉用户模拟器**：让用户模拟器通过调用手机侧只读工具获取自身状态，取代长文本 Prompt 硬背人设，将模拟器总出错率从传统域的 **40%–47%** 压降至 **16%**，且**未锚定胡编（幻觉）与漏约束降为 0%**。
4. **双端协同折损与复合症状掩盖实证**：揭示主流大模型一旦从单方控制进入 `telecom` 双端协同，$\text{pass}^1$ 集体跌破 50%（仅双端沟通引导就造成 **18%–25%** 的成功率折损），在存在“症状掩盖”的多故障彩信任务上 $\text{pass}^4$ 更是跌至 **2%–10%**。

## 二、三大核心算法与工程机制拆解

### 2.1 双端协同状态机与跨端同步算法 (`orchestrator.py` & `environment.py`)

```text
+-----------------------------------+                 +-----------------------------------+
|            Agent (LLM)            |                 |       User Simulator (LLM)        |
|  策略: Original / Workflow Policy |                 |  人设: None / Easy(67岁) / Hard   |
+-----------------+-----------------+                 +-----------------+-----------------+
                  |                                                     |
    (1a) 调后台工具|              (1b / 2b) 发送自然语言消息              | (2a) 调手机工具
    (控制权留在本方)| <----------- 触发半双工控制权交接 --------------> | (经 flip_roles 翻转)
                  v                                                     v
+-----------------------------------+                 +-----------------------------------+
|     Agent Tools (6 读 + 6 写 + 1) |                 |     User Tools (15 读 + 15 写)    |
|  查客户/账单/流量; 停复机/开漫游/ |                 |  看信号栏/测速/发彩信; 开关飞行/  |
|  发催缴单/流量加油包/转人工       |                 |  插拔SIM/改APN/关VPN/授权/付款    |
+-----------------+-----------------+                 +-----------------+-----------------+
                  |                                                     |
                  v                                                     v
+-----------------------------------+   sync_tools()  +-----------------------------------+
|      Agent DB (TelecomDB)         | <=============> |     User DB (TelecomUserDB)       |
|  plans / customers / lines / bills|  每次调工具后触发|  device (硬件设置) + surroundings |
+-----------------------------------+                 +-----------------------------------+
```

整套交互引擎由三条硬性状态流转规则驱动：

1. **半双工互斥与控制权交接（`orchestrator.py:737-746`）**：
   - **单步动作二选一铁律**：任意一轮输出，参与者**要么调用工具，要么向对方发文本消息**，严禁同一轮既调工具又说话（源码拦截同时含 `content` 与 `tool_calls` 的响应并报错重试）。
   - **控制权流转**：调用本端工具后，环境返回执行结果，**控制权继续留在本方手里**（支持连续查库排障）；只有发出自然语言消息时，控制权才移交给对方（上限 `MaxSteps=200`，连续工具报错上限 `MaxErrors=10`）。
2. **视角镜像翻转协议（`flip_roles`, `user_simulator_base.py:62-106`）**：
   - 大模型原生 Function Calling API 只允许 `assistant` 角色吐出 `tool_calls`。为了让用户模拟器也能操作手机工具，每次轮到用户行动前，引擎自动把对话历史做镜像翻转——将用户过往发言转为 `assistant`、将客服发言转为 `user`（并剥离客服私有的查库记录），驱动模型生成手机工具调用后再把发起方标签翻回 `"user"`。
3. **`sync_tools()` 四路跨端因果同步（`telecom/environment.py:40-95`）**：
   初始化及**每一次双端工具执行完毕后**，底层自动运行同步钩子打通物理因果：
   - **停复机传导**：后台 `line.status == ACTIVE` 实时覆写终端 `surroundings.line_active`；
   - **漫游权限传导**：后台 `line.roaming_enabled` 实时覆写终端 `surroundings.roaming_allowed`；
   - **流量超限断网传导**：计算后台已用流量是否触顶（`已用 >= 套餐额 + 加油包`），写入终端 `mobile_data_usage_exceeded`（一旦为真，用户测速直接掉为 `No Connection`）；
   - **催缴—付款双向闭环**：后台下发催缴单后自动在用户手机生成待付账单对象；用户在手机端调 `make_payment` 付款后，钩子立即回调后台将账单改为 `PAID` 并清空手机待付提示。

| 评测域      | 数据库体量                     | Agent 工具 (写 / 读) | User 工具 (写 / 读) | 评测题数             | 控制模式     |
|:----------- |:------------------------------ |:--------------------:|:-------------------:|:--------------------:|:------------ |
| **retail**  | 500 用户, 50 商品, 1,000 订单  | 7 / 6                | 无                  | 115                  | 单方控制     |
| **airline** | 500 用户, 300 航班, 2,000 预订 | 6 / 6                | 无                  | 50                   | 单方控制     |

### 2.2 组合式任务合成与“三步必要性验证”算法 (`domains/telecom/tasks/`)

为彻底消除人工编写多轮排障剧本的逻辑漏洞与“蒙答案捷径”，生成管线采用四步确定性流水线：

```text
[1. 定义原子故障单元 BaseTask]
   每个原子故障绑定 3 个Python函数: (init_funcs 注入故障, fix_funcs 标准修复动作, extra_env_assertions 清除断言)
          │
          ▼
[2. 归入互斥选择集 SelectionSet 求笛卡尔积] (create_tasks.py:63-77)
   同一硬件/业务属性上的冲突故障归入同一 SelectionSet (每组每次最多抽 1 个故障或抽 None)
   跨组求笛卡尔积组合 ──► 剔除故障数 < 2 的简单题
   *死锁兜底规则: 组合中只要含任意不可修故障 (fix_funcs=[None], 如合约过期/SIM锁死)，
                 整题自动标记 expected_failure=True，标准解强制覆写为 [transfer_to_human_agents]
          │
          ▼
[3. 三步确定性沙箱自验证] (TaskManager.verify_task, manager.py:197-227)  *核心防捷径算法*
   ├── Step A (基线健康检验): 加载干净默认环境，校验顶层目标 is_fixed(env) 必须为 True
   ├── Step B (逐步必要性检验): 运行全部 init_funcs 注入复合故障；按序逐个执行标准修复动作 a_1..a_m，
   │                          在【每一个动作 a_i 执行之前】强制断言 is_fixed(env) == False！
   │                          (但凡少修一步就已经恢复正常，说明存在冗余子故障，直接判废剔除)
   └── Step C (终态完备检验): 全部修复动作跑完后，断言 is_fixed(env) == fixable 且所有子断言全过
          │
          ▼
[4. 分桶采样] 全量合法题 2,285 道 ──► 按 (故障大类, 子故障数, 用户人设) 分桶抽样 (每桶 ≤3, seed=42) ──► 114 题
```

**三大故障意图组合规模与判据（`App. A.2`）**：

- **`service_issue`（无信号/无法通话）**：5 个互斥集（飞行模式、SIM 松动/锁死、账单逾期/停机/合约到期、手机/后台漫游关闭、2G 制式限制）；终态判据为信号栏恢复且非飞行模式；全量 47 题 $\rightarrow$ 采样 **29 题**（平均修复 2.31 步）。
- **`mobile_data_issue`（无数据/网速慢）**：7 个互斥集（1 个服务前置集 + 数据开关、漫游复合集、省流限速、APN 错误、VPN 限速/故障、流量耗尽）；终态判据为 `run_speed_test >= 100 Mbps (Excellent)`；全量 382 题 $\rightarrow$ 采样 **36 题**（平均修复 4.31 步）。
- **`mms_issue`（彩信发送失败）**：9 个互斥集（服务与数据前置集 + Wi-Fi 抢占蜂窝通道、Wi-Fi 通话干扰、彩信 MMSC 配置缺失、短信 App 存储/SMS 权限缺失）；终态判据为 `can_send_mms() == True`；全量 1,856 题 $\rightarrow$ 采样 **49 题**（平均修复 6.00 步，最高 12 步）。
- **绑定三类用户人设（Personas）**：`None`（默认）、`Easy`（67 岁退休教师，不懂手机设置但完全听指挥）、`Hard`（42 岁建筑工人，急躁易怒，讨厌反复排查）。

### 2.3 终态重放打分器与 $\text{pass}^k$ 可靠性算法 (`evaluator/` & `metrics/`)

1. **沙箱双副本重放评测（`EnvironmentEvaluator`, `evaluator_env.py:29-160`）**：
   评测器不纠结中间对话先问哪句、后问哪句，而是拉起两个完全一致的沙箱副本 `predicted_env` 与 `gold_env`：
   - 在 `predicted_env` 中按序重放对话里双端实际触发的**所有写状态工具调用**（自动跳过只读查询、`think` 与幻觉工具名）；
   - 在 `gold_env` 中执行预设标准解动作序列；
   - **可修复任务**：运行环境断言组 `EnvAssertionCheck`（顶层 `is_fixed` + 各子故障附加断言）判定业务是否真正恢复（单方域同时比对双库 SHA-256 哈希 `DBCheck`）；
   - **不可修复任务**：联合校验环境断言与动作轨迹 `ActionEvaluator`——必须实际调用了 `transfer_to_human_agents` 才给满分；若超步数（200 步）或连续报错超限（10 次）直接记 0 分。
2. **多次运行一致性指标 $\text{pass}^k$**：
   每道题独立重跑 $n=4$ 次，假设拿到满分的次数为 $c$，要求**任意抽 $k$ 次全部稳定成功**的无偏概率为：
   $$\text{pass}^k = \mathbb{E}_{\text{task}}\left[\frac{\binom{c}{k}}{\binom{n}{k}}\right]$$
   直白理解：$\text{pass}^1 = c/4$ 是常规单次平均成功率；而 $\text{pass}^4$ 极其严苛——4 次测试里哪怕只有 1 次发挥失常（$c=3$），分子 $\binom{3}{4}=0$，该题直接记 0 分，专门惩罚生产环境中“时灵时不灵”的脆弱 Agent。

### 2. 三联消融实验：钱到底输在“不会推理”还是“不会教用户”？ (`Fig. 4`, $\text{pass}^1$)

作者在 `telecom` 上用两组文档（声明式业务规则 `Original Policy` vs. 手把手排查流程图 `Workflow Policy`）交叉对比三种控制模式：

- **`Default`**：标准双端协同；
- **`No-User`（Solo 单人全控）**：砍掉用户模拟器，把手机 30 个工具全塞给 Agent 自己调（剥离沟通成本，纯测排障推理）；
- **`Oracle Plan`（给标准答案剧本）**：保持双端隔离，但把标准修复动作序列直接写进 Agent 提示词（剥离诊断推理成本，纯测引导用户执行力）。

| 策略文档与模型           | Default (标准双控) | No-User (单人全控) | Oracle Plan (给标准剧本) | 双端沟通折损 (Default - No-User) | 诊断推理缺口 (Oracle - Default) |
|:------------------------ |:------------------:|:------------------:|:------------------------:|:--------------------------------:|:-------------------------------:|
| **Original** + `gpt-4.1` | 0.34               | 0.52               | 0.73                     | **-18%**                         | +39%                            |
| **Original** + `o4-mini` | 0.42               | 0.67               | **0.96**                 | **-25%**                         | +54%                            |
| **Workflow** + `gpt-4.1` | 0.52 (+18%)        | 0.68 (+16%)        | 0.57 (-16% vs Orig)      | **-16%**                         | +5%                             |
| **Workflow** + `o4-mini` | 0.59 (+17%)        | 0.72 (+5%)         | 0.88 (-8% vs Orig)       | **-13%**                         | +29%                            |

**三条极具工程指导价值的实验发现**：

1. **光“张嘴教用户干活”就掉点 18%–25%**：同样的排障逻辑，一旦把手机工具收归用户、必须靠多轮对话询问现象并指导操作，成功率立刻大幅缩水（推理模型 `o4-mini` 掉得最狠，达 -25%）。
2. **显式排查流程图（`Workflow`）大涨常规表现，但与捷径剧本打架**：换成步骤级排障手册后，`Default` 模式直涨 17%–18%；但在已给最短答案的 `Oracle Plan` 下反而倒退 8%–16%——因为模型死板遵守手册固定排查顺序，与最短修复剧本产生了指令冲突。
3. **非推理模型拿着答案也不会带人**：`Original + Oracle Plan` 下 `gpt-4.1` 仍有 **27%** 失败率（0.73），说明把技术动作翻译成通俗抗歧义的用户指令是独立能力瓶颈。

### 3. 症状掩盖效应、急躁人设冲击与模拟器零幻觉验证 (`Fig. 5–7, Table 2`)

- **复合故障的“症状掩盖效应（Masking Effect）”导致彩信题崩盘**（`Fig. 6`）：
  简单信号题 `service_issue` 上 `o4-mini` 可达 `0.85 / 0.76`（$\text{pass}^1/\text{pass}^4$）；但到了平均 6 步修复的 `mms_issue`，四模型 $\text{pass}^1$ 暴跌至 **`0.12–0.18`**，$\text{pass}^4$ 仅 **`0.02–0.10`**。典型死因是“局部好转即提前收工”——如同时存在流量耗尽与省流模式限速时，Agent 充完流量包见网速从 `0` 升至 `55 Mbps (Good)` 便以为修好挂断，漏掉了关省流模式恢复 `>=100 Mbps (Excellent)` 的隐藏故障。
- **急躁用户（`Hard Persona`）显著击穿引导稳定性**（`Fig. 7`）：相比配合度高的 `Easy` 老人人设，面对不耐烦的 `Hard` 建筑工人时，`claude-3.7-sonnet`、`gpt-4.1-mini`、`o4-mini` 的 $\text{pass}^1$ 分别大幅下滑 **-0.21**（`0.63->0.42`）、**-0.20**（`0.54->0.34`）和 **-0.14**（`0.52->0.38`）。
- **工具化状态彻底消灭用户模拟器幻觉**（`Table 2` 人工抽检）：

## 五、向联接 Agent（主报告）的四大落地映射

直接对齐主报告 [storyline_and_evaluation_merged_technical_route_report.html](file:///d:/coding/sharing/.lavish/storyline_and_evaluation_merged_technical_route_report.html) 的合成数据与端到端评测模块：

1. **升级合成数据管线：正交 `SelectionSet` + 逐步必要性校验（防蒙对捷径）**
   将用户长期记忆槽位与网元实时状态拆为互斥选择集（`主力业务应用集` × `周期作息窗集` × `网元并发劣化集` × `模糊指代习惯集`），每个合成样本绑定 `(f_init, f_sol, f_assert)`。生成期自动运行 `verify_task` 逻辑——**强制验证若漏查某条历史记忆或少走一步慢路径澄清，最终保障单据断言必然不通过**，彻底剔除不查记忆也能蒙对的伪多轮样本。
2. **改造用户模拟器：结构化快照只读工具 + `flip_roles`（根除测试幻觉）**
   弃用把整段人设故事塞进长 Prompt 的传统做法，将当前回合的 `Ground-Truth Memory Snapshot` 与终端卡顿指标封装成用户侧只读查询字典。当联接 Agent 走慢路径追问（如确认加速 App、保障时长或本地信号表现）时，让模拟器通过确定性工具读取真值作答，把测试集自身幻觉率压到 0%。
3. **引入三联消融基线：精准剥离“检索锅、澄清锅、填参锅”**
   仿照 `Default / No-User / Oracle Plan` 对照矩阵，在端到端评测旁同步跑两组消融基线：
   - **`Oracle Memory`**：直接注入完美召回的黄金记忆槽位（剥离检索引擎漏召回误差）；
   - **`No-Clarification`**：直接给定无歧义完整诉求走快路径（剥离多轮慢路径沟通折损）。
     用三组差值直接定位版本迭代时的真实掉分瓶颈。
4. **锁死上线门禁：`ENV_ASSERTION` 沙箱终态重放 + $\text{pass}^3$ 红线**
   不考核中间追问话术的字面重合度，统一在沙箱中重放最终写操作单据（如 `create_qos_guarantee_ticket`），联合校验网元配置终态断言与越权/异常场景下的安全兜底动作（`ACTION`）；同时弃用虚高的单次 $\text{pass}^1$，将 $n \ge 3$ 次独立试验全部通过的 **$\text{pass}^3$** 定为生产准入硬指标。
