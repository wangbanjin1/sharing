## 一、核心思路与四大实证贡献

### 1. 核心破局思路 (`Sec 1, Sec 3.1`)

长程探索任务（如仓库级修 Bug，单次跨越数十至上百回合、长 `55K–170K` Token）中，传统“任务开局一次性检索塞入（Eager Injection）”全面失灵，根源在三处：

1. **粒度两极分化**：存 `105K` 原始长轨迹会被海量废分支稀释检索信号（`Match@1` 仅 `22.2%`），塞进上下文还会喧宾夺主挤占模型自主探索（回合数从 70 跌至 50，坏补丁 `PatchNA` 从 7 恶化至 11）；切碎成 `12–30` Token 原子事实块（如 `Mem0`、`Supermemory`）又打断了“定位—根因—修复—验证”的因果链（`Match@1` 仅 `23%–25%`）。
2. **实际吸收率极低**：标识符探针实测表明，模型仅引用了注入原始轨迹中 **26.7%–27.2%** 的关键标识符，散文摘要也仅吸收 **45.7%–52.5%**。
3. **无视运行态处境与滞留污染**：Agent 顺风顺水时强塞外部代码细节纯属干扰；只有当验证受挫（Struggling）时才需要重型实现参考，且参考完若一直钉在上下文前缀（Pinned），会在后续几十回合持续把模型往旧任务的特定改法上死拽。

**REM 的解法是将静态查找升级为循环内三决策控制策略**：

- **存什么（双层分离）**：`Tier 1` 压成 ~270 Token 的**四阶段诊断导航卡**（既当检索索引又驻留开局导航）；`Tier 2` 抽出 $\le 12\text{K}$ 字符的**原始代码修改与验证记录**（开局严格扣留）；
- **何时召回（受挫门控）**：循环内实时盯盘，仅当遭遇**首次真实测试/校验失败**（排除编辑测试文件本身的预期报错）时，才把 `Tier 2` 重型记录调入下一回合救援；
- **何时遗忘（单次曝光即驱逐）**：`Tier 2` 记录仅在受挫后曝光 **1 个回合**，紧接着下一回合立刻从上下文前缀彻底踢出（不占后续 KV Cache，消除长尾锚定偏置）。

### 2. 四大核心贡献

1. **检用合一的四阶段压缩表征（`>100×` 压缩比）**：先剥离工具返回结果缩减 15 倍，再按「定位—根因—修复—验证」抽取渲染为 ~270 Token 文档；仅凭普通余弦检索（未重排 `65.7%`）即击败 `LangMem` 重排后精度（`55.6%`），重排后 `Match@1` 达 **`68.7%`**（大幅甩开 `Mem0` `25.3%` 与同体积 `OpenViking` `38.4%`）。
2. **零人工工程的自动 Schema 发现元循环**：仅靠经验池中 **9 条无标签轨迹**与五维 LLM Judge 打分，1 轮迭代即自动收敛出剔除浏览噪声（删 `files_read`）、强化报错表征（增 `error_messages`）的 8 字段模板，检索精度反超人工手写 Schema（`68.7%` vs `66.7%`）。
3. **标识符吸收探针与门控/驱逐消融实证**：证明开局给先知真值原始轨迹（`24.2%`）或散文摘要（`23.2%`）均不涨分，唯有 `REM` 将吸收覆盖率推至 **`69.1%`**，端到端解决率升至 **`27.6%`**，同时单题 Token 成本降 **17%**、耗时省 **26%**、坏补丁减 **43%**；并定量拆解出“不门控急切注入掉 2.3 点、注入后常驻不驱逐掉 2.7 点”。
4. **揭示经验记忆的“能力收益带宽（Capability Band）”反转律**：横跨 5 档基座模型（裸跑 `20.2%` 至 `52.5%`）实测发现，经验记忆仅对中弱能力模型产生净增益（`+2.7 ~ +4.1 pp`）；一旦底座自身解决率跨过 ~45% 门槛（`Opus 4.8 / Sonnet 5`），哪怕注入 100% 正确的 `Oracle` 文档也会造成 **`-2.0 ~ -9.1 pp` 的显著负迁移**。

## 二、核心机制拆解：三决策管线、自动 Schema 与吸收探针

```text
【离线写路径：Decision 1 - 存什么 (双层产物生成)】
   原始长轨迹 (55K–170K tok)
     ├─► 1a. 无损拍平 (Flatten): 仅留对话推理与工具入参，直接丢弃冗长工具返回文件内容 (~15× 缩减)
     ├─► 1b. 四阶段导航卡 (Tier 1, ~270–305 tok, >100× 压缩):
     │         调 1 次 LLM 抽 8 个核心字段 ──► 确定性模板渲染 [Localize → Understand → Fix → Verify]
     └─► 1c. 重型实现记录 (Tier 2, ≤12K 字符 / ~3K tok): 提取真实代码修改 diff 与验证命令记录

【在线读与控制路径：Decisions 2 & 3 - 何时召回、何时遗忘】
   新任务启动 (t = 0):
     问题 q ──► Titan Embed v2 余弦搜 Top-5 导航卡 ──► 1 次 LLM 重排选出最优对 (Tier1_doc, Tier2_record)
     • Tier 1 导航卡: 写入初始必读文件，全程轻量驻留引导大方向
     • Tier 2 实现记录: 开局严格扣留不注入！
          │
          ▼  进入最多 100 回合的 Think-Act 循环 (t = 1..100)
     每步监测环境反馈 ──► 是否触发【受挫门控 Struggle Gate】？
       (触发条件: 首次出现真实测试/校验命令报错，显式排除修改测试文件自身引发的预期报错，且本局未触发过)
       ├── 是 (首次受挫): 【Decision 2 召回】下一回合临时拼入 Tier 2 实现记录救援，并锁死门控开关
       └── 否 (未受挫，或上一回合刚曝光过): 【Decision 3 遗忘】立即将 Tier 2 记录从活跃上下文前缀清空 (One-Shot Eviction)
```

### 1. 自动 Schema 发现：为什么自动找的 8 个字段比人写的更准？（`Sec 3.3, App F`）

不用人工拍脑袋定抽取模板，直接从历史池抽 **9 条无标签轨迹**（严格隔离测试集）跑“生成抽取 Prompt $\rightarrow$ 试抽 $\rightarrow$ 5 维裁判打分（覆盖度/特异性/可区分度/简洁性/一致性，满分 5 分，均分 $\ge 4.0$ 即停）”自迭代，代码修复与 Text-to-SQL 均**第 1 轮即收敛**。对比人工 9 字段与自动发现 8 字段的关键差异（`Table 14`）：

- **砍掉浏览噪声（防稀释向量）**：人工模板保留了 `files_read`（只读未改的大量无关文件）与宽泛的 `key_identifiers`，严重拉偏检索向量；自动 Schema **直接剔除这两项**，并将函数/类、测试名/测试命令分别合并为精简的 `related_functions` 与 `test_cases`。
- **补齐故障表征（对齐新问题）**：自动 Schema 主动新增了人工漏掉的 **`bug_description`、`repository_info`、`error_messages`** 三项——少记“当时逛了哪些文件”，多记“当时报了什么错”，检索时正好与新任务的 Issue 报错文本精准咬合。

### 2. 上下文吸收率探针怎么测？（`Identifier Utilization Probe`, `Sec 3.3, App G`）

把注入记忆里所有文件路径与长度 $\ge 4$ 的驼峰/下划线代码标识符拎出来（扣除停用词，并扣除无记忆基线靠自己本来就能搜到的词），统计它们真正出现在 Agent 后续自主思考和工具入参里的比例：

- **吸收覆盖率（Coverage）**：真正被用上的标识符占比（实证发现成功解题运行的吸收率显著高于失败运行，$p=0.03$）；
- **无效滞留比（Dead Weight）**：最后一次引用某记忆之后，该记忆继续白占上下文前缀的剩余回合比例（例如注入无关摘要时高达 `96.3%` 纯属死重负担）。
