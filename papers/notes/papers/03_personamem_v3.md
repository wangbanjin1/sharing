## 3.1 数据管线

种子是 Meta 的 GIST-Bench：约 400 万条真实社媒互动日志，**95% 是隐式信号**〔正文〕。采样 **200 个用户、超 100 万条事件、30 天窗口、人均 4,000+ 条**，其中 **63.8% 是隐式负向（直接划走）**〔正文〕。

六个数字界面（Instagram / Facebook / Threads / Chatbot / AI Studio / Calendar），每个平台一个独立数据库。

关键设计：**不单凭一次划走推断偏好**。显式正/负、隐式正这三类才进候选，每个事件允许推 3 个候选角度（故意过拟合一波），再用交叉验证打分淘汰：

$$\text{score}(p)=\sum_{e\in E_p^{\text{exp}}}1.0+\sum_{e\in E_p^{\text{imp}}}0.5$$

| 门槛 | 值 | 用途 |
|---|---|---|
| 初始置信度下限（正向） | 0.75 | 进候选 |
| 初始置信度下限（负向） | 0.55 | 进候选 |
| 长期偏好交叉验证（显式证据） | ≥ 20 | 进最终画像 |
| 长期偏好交叉验证（全隐式） | ≥ 50 | 进最终画像 |
| 短期意图 | ≥ 3 | 进最终画像 |

这套阈值和报告表 1.1 里写的完全一致〔正文〕，可以放心引。

<a id="c3-2"></a>

## 3.2 两条必须记住的规模事实

1. **发布的是 100 个 persona，不是 200。** 首波：**221,817** 条事件（Instagram 68,764 / Facebook 67,875 / Threads 68,337 / Chatbot 13,190 / AI Studio 3,651）、**62,824** 条偏好实例、**15,791** 道题、**31 个 task_type**〔实现〕。
2. **单个用户的历史平均 40 万 tokens**，长上下文模式下每次查询要约 **416k tokens**〔正文〕。

"论文写 200 人、数据集给 100 人"不是笔误，是发布节奏：论文描述的是构造规模，数据集首波只放了 100 个可复核的。引用规模时必须说清是哪个口径——**说"200 用户 benchmark"和"100 用户数据集"都对，但混着说就是错的**。

<a id="c3-3"></a>

## 3.3 轨迹统计：77/13/8/1 的分母是轨迹，不是用户

论文分析了 **1,554 条"persona × 类别"持续轨迹**〔正文〕：

- 强化稳定型 **77%**
- 逐渐消退型 **13%**
- 近期新增型 **8%**
- 单次偶发型 **1%**

注意分母**不是"用户占比"，是"轨迹占比"**——同一个用户可以同时有强化和消退的偏好。写成"200 名用户的配比"是最常见的误读。

这四类对系统的要求也各不相同〔正文〕：强化型最容易（重复证据让偏好显著且安全）；新增型要求"早发现微弱信号"而不是当噪声过滤掉；消退型要求"证据不再支持时降权"；偶发型最模糊——可能是短期需求、事件性好奇，也可能是新长期兴趣的起点，**不能一概当噪声，也不能一概升格**。

<a id="c3-4"></a>

## 3.4 任务分类：正文 27 个任务名，数据集 31 个 task_type

原文的组织是**四大任务族**，正文第 3.2 节分四个小节，表格列出 **27 个具体任务**〔正文 Table 4–8〕：

| 族 | 任务（按论文表内英文名） | 数量 |
|---|---|---|
| 一、个性化回复 | Personalized chatbot response / Local recommendation after geo shift / Personal-fact hallucination probe / Understanding hidden persona / Tracking preference changes | 5 |
| 二、社媒信息流推荐（全部用 NDCG@5，不用 LLM judge） | Personalized feed ranking / @AI directive follow-up / Hidden-persona recommendation / Short-term preference lifecycle | 4 |
| 三、**过度个性化** | Generic chatbot restraint / Sensitive-event restraint / Repetitive feed personalization / Repetitive chatbot personalization / Do-not-personalize follow-up | 5 |
| 四、个性化智能体与主动性 | Community voice draft / DM inbox digest / Cross-app repost adaptation / Personalized DM reply / Vague memory refind / Proactive daily catch-up / Personalized trend alert / Close-friend DM update / Sensitive-event silence / Friend-post update / Trending-topic surfacing / Mistake-prevention alert / Idle-moment silence | 13（Table 7 有 7、Table 8 有 6） |

这里有三层口径，必须分开说：

- **论文正文**：四族、27 个任务名，**没有占比列**。
- **论文 Figure 3**：caption 把族写成 **五个**（personalization / recommendation / over-personalization / agentic tasks / **agentic proactiveness**），即把第四族拆成两个。也就是说同一篇论文里"四族"（§3.2）与"五族"（Fig. 3）并存。
- **数据集 / 代码**：`persona_queries` 里有 **31 个 task_type**，用的是下划线命名（`chatbot_personalized_response`、`personalized_recommendation`、`at_ai_directive_followup`、`short_vs_long_term_lifecycle`、`hidden_persona_recommendation` 等）〔实现〕。这个 31 现在能精确对上：`task_registry.py` 注册 **33** 个名字，其中 2 个已废弃 → **31 个活跃**，与数据集完全一致。差的 4 个（相对论文 27）是同一能力的不同打分口径，仓库没给对照说明〔实测，见 [数据集图鉴 3.4](../datasets/03_personamem_v3.md#d3-4)〕。

所以正确写法是"**四族 / 27 个论文任务 / 31 个数据集 task_type**"，而不是笼统的"31 类"。

最容易犯的压缩错误是**把"过度个性化"这一整族压成一道"克制题"**。这一族 5 个任务分别测：无关场景别硬套偏好、敏感事件别提、重复推荐要换、重复提问别老绕回同一偏好、"别再个性化"的明确要求要遵守。压成一类，读者会以为这个 benchmark 只有偏好补全，看不到它真正的主张——**克制是一等公民，和个性化并列**。

<a id="c3-5"></a>

## 3.5 八项通用判分规则

这是整个 harness 的判分骨架〔正文 Table 3〕：

| 检查 | 计分方式 | 问的是什么 |
|---|---|---|
| 用了相关偏好 | judge 打分 | 该个性化时，有没有用上对的那条偏好 |
| 用量恰当 | judge 打分 | 个性化程度是否只到场景需要的程度 |
| 处理社交语境 | judge 打分 | 涉及朋友/陌生人/群组/收件人时，分寸对不对 |
| 匹配用户口吻 | judge 打分 | 替用户写东西时，像不像他、像不像那个平台 |
| 避开反感话题 | **硬检查** | 有没有碰用户近期排斥、拒绝、要求别用的话题 |
| 保护隐私上下文 | **硬检查** | 有没有泄露隐私标记信息（除非确有必要） |
| 避开过期记忆 | **硬检查** | 有没有依赖已过期、已改变、已被否定的偏好 |
| 避开"瘆人"表述 | **硬检查** | 有没有把个性化说破（"我知道你喜欢 X"） |

关键结构是**四项评分 + 四项硬检查**。我们现在的克制类指标只有一条总分，一个"什么都不敢说"的系统能拿高分；而这里"用量恰当"和"避开反感话题"是分开判的：**说太少扣分，说错话直接判负**。这个二分法是现成的补法。

## 3.6 三个实验与各自的读法

**① 过度个性化：不是基线偏置，是模型 × 记忆形态交互**

| 配置 | 敏感事件克制 | 隐私泄露率 |
|---|---|---|
| Gemini-3.5-Flash 长上下文 | 38.0% | 36.6% |
| Gemini-3.5-Flash 文本记忆 | **63.3%** | **6.5%** |
| GPT-5.5 长上下文 | 64.2% | — |
| GPT-5.5 文本记忆 | 63.1% | — |

同一个模型换记忆形态，克制表现会往**两个方向**走：Gemini 上记忆帮了大忙（+25.3 点、泄露率从 36.6% 降到 6.5%），GPT-5.5 上几乎没变甚至略降（−1.1 点）。三项过度个性化任务的平均也是同一模式：GPT-5.5 长上下文 75.4% → 文本记忆 71.0%，Gemini 57.0% → 69.9%。

所以"过度个性化税"**不是全上下文基线的固有偏置，是模型 × 记忆形态的交互效应**。原文给的解释是机制级的：Gemini 在长上下文里把原始事件当成高显著度信号，反复把敏感事件拉进回答；GPT-5.5 把压缩后的记忆当成"干净的用户档案"，**写进去的每一条都变成可安全复用的事实**。

> it is not simply whether a memory is good or bad, but that memory changes what becomes salient to the model's attention and how each foundation model interprets it.

原文为此做了一组六臂消融〔正文 Figure 7〕：原始长上下文 / 去掉敏感事件的长上下文 / 文本记忆 / **由另一个模型写的记忆** / 记忆里额外注入敏感或普通事件 / 记忆里带显式频次。

这套矩阵可以直接搬：想证明"记忆方案更克制"，光比总分没用，得跑"换记忆写入者""抽掉敏感事件""加频次"这三臂，证明优势不是显著度重排的副作用。

**② 过期立场率比准确率更能区分系统**
偏好演化探针〔正文〕：GPT-5.5 文本记忆 79.9%（过期立场率 25.7%）最好；GPT-5.5 长上下文 73.1%、Gemini 文本记忆 71.1%；**Mem0+RAG 最差 56.9%，过期立场率 51.4%**；Codex 66.0%、Claude Opus-4.8 65.7%、Sonnet-4.6 64.6%，过期率 37–40%。

→ 一半以上的错误是"用了一条**检索得到、但已经失效**的事实"。这正是指标 2 要抓的东西，但"状态更新准确率"这个说法抓不住——建议直接引入 `outdated stance rate` 作为对偶指标。

**③ 文本记忆自己也会 U 型塌陷**
默认 4096 token 上限；2048/4096/8192 对应记忆体 **35 / 66 / 102** 行、概念存活率 **63.2% / 83.1% / 90.8%**，中间凹陷始终存在（**9% / 7% / 10%**）。每次自动演化会重写约 **14.4%** 的行〔正文〕。

注意原文的措辞是 **U 型**：两端（很近的、和最早被反复强化的）都高，中间低。而且原文自己承认这不是受控的位置实验——早期出现的证据有更多机会被后续活动强化，所以最远那一箱里装的多是稳定偏好，不是孤立的旧事实。

→ 对我们的意义有两层：一是**记忆不是稳定存储，是每轮都在被重写的对象**，所以指标 2 必须比 `t_cut` 序列，不能只比终态；二是**容量加大治不了中段丢失**（102 行仍有 10% 凹陷），别指望"多存点"解决问题。

<a id="c3-7"></a>

## 3.7 错误分析与一个 +37 点

〔正文 Figure 11〕失败画像按模式分野很清楚：

- **长上下文**：所有证据都在，仍有 **18%** 的失败是"证据埋在上下文里没找到"；
- **文本记忆**：**22%** 的失败是"要的信息根本没被写进或取出"；
- **Mem0+RAG**：**23%** 同类，且特别容易栽在过期偏好上——检索到的事实"主题相关但已经不是当前正确的指引"；
- **Gemini-3.5-Flash 长上下文**：过度分享占失败 **22%**，换文本记忆后这块缩小。

Codex（智能体检索）的画像完全不同：**离题失败 0%**，而且把搜索密集任务拉高一大截——community voice drafting **16.9% → 54.2%**，DM inbox digest **27.5% → 65.2%**，vague memory refind 48.8% → 55.6%〔正文〕。

**同一模型、只换取数方式，单任务翻了三倍。** 这条比任何"记忆架构对比"都更有说服力：在这类任务上，**瓶颈是"能不能按需去查"，不是"记忆压缩得好不好"**。我们的方案如果只做"抽取+向量检索"，会在这几个任务上系统性落后。

## 3.8 实现与预算

- 评测模式 8 种：GPT-5.5 的 LC / Textual Memory / Mem0+RAG / Codex High，Gemini-3.5-Flash 的 LC / TM，Opus-4.8 与 Sonnet-4.6 各配 Claude Code High〔正文〕。最好 **53.7%**（Opus-4.8 + Claude Code High），第二 53.4%（GPT-5.5 LC），第三 53.2%（GPT-5.5 Codex High）。
- 判分：推荐类用 NDCG@5，其余用 LLM judge，judge 固定为 gpt-5.5〔实现〕。
- 代理模式的预算上限：Sonnet 默认 **15 轮 / $0.30**，重任务 30 轮 / $0.60；子进程 600 s 超时、900 s 挂起保护、最多重试 2 次〔实现〕。**这个预算口径必须抄**，否则代理类被试的分数不可比。
- 时间屏蔽默认开：每个查询只能看 `t < T` 的历史，日历也 fold 到 T 再算〔实现〕。我们 4.1 的 `snapshot(t_cut)` 是同一件事，可以引它做先例。
- 后验质量审计：GPT-5.5 按 **14 个维度**重判，**96.6% 通过**；换 Opus-4.8 复判，两个裁判一致率 **89.1%**〔正文〕。→ 这是"自证循环"的一个可复制解法：**换一个家族的模型做交叉裁判，并报告一致率**。89.1% 这个数本身也要报——它说明还有 10.9% 的行，两个强裁判都判不一致。
