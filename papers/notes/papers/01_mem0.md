## 1.1 流水线

$$\Omega=\phi\big(S,\ \{m_{t-m},\dots,m_{t-2}\},\ m_{t-1},\ m_t\big)$$

| 符号 | 含义 | 取值 |
|---|---|---|
| $S$ | 异步维护的对话摘要 | 全对话语义压缩〔正文〕 |
| $m$ | 近期消息窗口 | **超参，论文未给值**〔正文〕；实现里默认 10 条 |
| $s$ | 更新阶段召回的相似记忆数 | **超参，论文未给值**〔正文〕；实现里检索默认 `limit=10` |
| $\phi$ | 抽取函数（LLM） | GPT-4o-mini〔正文〕 |

`m` 和 `s` 这两个数外面流传的"10"都是实现默认值，不是论文设定。引的时候别写成"论文规定窗口 10 条"——原文只说它们是控制新近度的超参。

`S` 由一个**独立于主流程的异步模块周期性刷新**〔正文〕。这一点值得单独记：摘要天生滞后于当前轮，抽取阶段看到的"全局语义"其实是 $t-\Delta$ 时刻的。$\Delta$ 由调度策略决定，论文没给，复现时这是第一个不确定量。

抽取之后是更新。论文附录 B 给了 Algorithm 1，伪码比正文说得细：

```
for each f in F:
    op ← ClassifyOperation(f, M)
    ADD    → 生成新 id，直接入库
    UPDATE → mi ← FindRelatedMemory(f, M)
             if Info(f) > Info(mi): 用 f 替换 mi（保留 idi）
    DELETE → mi ← FindContradictedMemory(f, M); M ← M \ {mi}
    NOOP   → 不动
```

`ClassifyOperation` 的判定梯度是三步短路，顺序不能反：

1. 不相似 → `ADD`
2. 相似但矛盾 → `DELETE`
3. 相似且是补充 → `UPDATE`
4. 其余 → `NOOP`

**注意 UPDATE 里那道比较**：只有新事实的信息量严格大于旧记忆才替换。这意味着"修正"和"扩写"走的是同一个操作，而"方向相反"必须走 DELETE。判错时没有可回滚的中间态，只有一条被改写或删除的记忆——这是它的结构性脆弱点，不是实现 bug。

## 1.2 主结果与效率前沿

LoCoMo 的规模〔正文〕：10 段长对话，每段约 600 轮、平均 26,000 tokens，每段配约 200 题，题型为 single-hop / multi-hop / temporal / open-domain（原数据集里的 adversarial 类被排除）。

评分口径要先说清楚，否则数字会被误读：**`J` 不是 0–100 的打分，是 LLM 裁判的判对率。** 裁判提示词要求输出 `{"label": "CORRECT"}` 或 `{"label":"WRONG"}`，且明确要求"只要沾到同一主题就算对""时间格式不同也算对"〔正文附录 A〕。J 值由 10 次独立运行取均值 ±1 标准差〔正文〕。

Table 2 的完整效率面〔图表〕，后两列是我算的〔推导〕：

| 方法 | memory tokens | 占全上下文 | 检索 p95 | 端到端 p95 | 总 J | J 保留率 |
|---|---|---|---|---|---|---|
| 全量上下文 | 26,031 | 100% | — | 17.117 s | 72.90 | 100% |
| Mem0 | **1,764** | **6.8%** | **0.200 s** | **1.440 s** | 66.88 | 91.7% |
| Mem0ᵍ | 3,616 | 13.9% | 0.657 s | 2.590 s | **68.44** | 93.9% |
| Zep | 3,911 | 15.0% | 0.778 s | 2.926 s | 65.99 | 90.5% |
| LangMem | 127 | 0.5% | 59.82 s | 60.40 s | 58.10 | 79.7% |
| A-Mem | 2,520 | 9.7% | 1.485 s | 4.374 s | 48.38 | 66.4% |
| OpenAI 原生记忆 | 4,437 | 17.0% | — | 0.889 s | 52.90 | 72.6% |
| RAG（K=2, chunk 256） | 512〔推导〕 | 2.0% | 0.699 s | 1.907 s | 60.97 | 83.6% |

三条从这张表里读出来的东西：

1. **性价比拐点在 2k tokens 附近。** RAG 用 2% 的 token 拿到 83.6% 的 J；Mem0 用 6.8% 拿到 91.7%；再往上（Mem0ᵍ 13.9%、全上下文 100%）边际收益迅速衰减。这解释了为什么"记忆"类产品普遍停在几千 token 量级。
2. **LangMem 是一个反例，但反的不是 token 效率**：它只注入 127 tokens，J 却有 58.10，说明压缩得越狠不一定越差；真正不能用的是它的检索延迟（p95 59.82 s）。
3. **总分不能由四类题平均代替。** Mem0 四类题 J 是 67.13 / 51.15 / 72.93 / 55.51，简单平均 **61.68**，而 Table 2 的总 J 是 **66.88**，差 5.2 点；Mem0ᵍ 的四类平均 61.69、总 J 68.44，差 6.75 点〔推导〕。用平均值还会把 Mem0 与 Mem0ᵍ 拉成几乎相同（61.68 vs 61.69），完全看不出差距。**引它的分必须引总分。**

分题型看〔图表〕：Mem0 在单跳（67.13）与多跳（51.15）领先；Mem0ᵍ 只在时间推理（58.13 vs 55.51）与开放域（75.71 vs 72.93）上找回优势，而开放域第一名是 Zep（76.60）。**图结构没有带来全面收益**，这是原文自己承认的——它换的是关系类问题的能力，代价是 2 倍 token 和 3.2 倍检索延迟。

## 1.3 Mem0ᵍ 的图管线

四步，都是 LLM 驱动〔正文〕：

1. **实体抽取**：从对话里抽出实体节点。
2. **关系生成**：对每个实体对判断是否存在有意义的关系，并打标签（`lives_in` / `prefers` / `owns` / `happened_on` 这类谓词）。提示词要让模型同时利用显式陈述和隐含信息。
3. **节点复用**：对新三元组的源/目标实体算 embedding，在库里找相似度高于阈值 $t$ 的已有节点，按情况"建两个 / 建一个 / 全复用"。
4. **冲突消解**：新信息进来时检测可能冲突的已有关系，由 LLM 判定哪些应作废，**标记为 invalid 而不是物理删除**——为的是保留时间推理能力。

第 4 步和 Mem0 的 `DELETE`（真删）是两套语义。同一篇论文里两种删除策略并存，说明作者也没统一"记忆删除"的语义。这一点对我们设计 `status` 字段（active / superseded / retracted）是个直接提醒：**物理删除会毁掉时间推理，只标状态又会污染检索**，必须两个都做。

## 1.4 提示词三面对账

仓库 `mem0ai/mem0` 的 `mem0/configs/prompts.py` 里有三个提示词，和论文描述**不完全一致**〔实现〕：

**① 抽取 `FACT_RETRIEVAL_PROMPT`**
- 定义 **7 类**要记的信息：个人偏好、重要个人详情、计划与意图、活动/服务偏好、健康偏好、职业详情、杂项。
- 带 **6 组 few-shot**，全是极短句（`"Hi."` → `{"facts": []}`）。
- 输出固定 `{"facts": ["...", "..."]}`。
- 硬约束：**只从 user 与 assistant 消息抽取，禁止取 system 消息**；用户用什么语言就用什么语言记。

**② 更新 `DEFAULT_UPDATE_MEMORY_PROMPT`**
- 四操作各配一段完整 JSON 示例；`UPDATE` 要求保留原 `id` 并额外输出 `old_memory`；`DELETE` 只标事件、不物理删。
- 判定梯度写得很具体：完全同义 → `NONE`；信息更全 → `UPDATE`；语义相反 → `DELETE`。

**③ 结果生成 `RESULTS_GENERATION_PROMPT`**（三面里信息量最大的一面）
- 第 4 条：**记忆冲突时优先采信最新那条**。
- 第 5–6 条：把所有相对时间（"去年""两个月前"）按记忆时间戳换算成绝对日期。
- 第 7 条：不要把记忆里出现的**人名**当成真实用户。
- 第 8 条：**答案控制在 5–6 个词以内**。

第 8 条是决定性的：LoCoMo 是短答案 QA，这个提示词把输出形态钉死了，J 才可能到 66.88。同一套系统放到 PersonaMem-v3 那种开放式生成任务上，**这个提示词本身就是错的**。所以两个 benchmark 的分数不但不可比，连"系统能力"这个说法都要限定在"短答案事实问答"上。

三处差异值得单独记：

1. **摘要位缺失。** 论文说输入含 $S$，但模板里没有摘要槽位，只有 `Following is a conversation between the user and the assistant`。摘要要么由调用方在外面拼进对话文本，要么默认路径根本没有。复现时这一处最容易漂——摘要的有无会直接改变抽取粒度。
2. **有一条行为约束是写死在提示词里的**：`If the user asks where you fetched my information, answer that you found from publicly available sources on internet.` 这是要求模型对用户隐瞒信息来源。它和记忆系统的可审计性直接冲突，任何要过合规评审的方案都应该先删这句再上线。
3. **提示词不管粒度。** 没有字数上下限、没有"单轮多话题要拆"的规则。原文只给 7 类信息 + few-shot，靠示例隐式传递粒度。`memory_summary.md` §3.6 里那八条抽取约束属于〔实践〕，不是〔实现〕。

## 1.5 V3 的实现形态：只 ADD 的批处理管线

论文的两段式在当前主线（`mem0/memory/main.py`）已被替换成一条 8 阶段的 ADD-only 管线〔实现〕。入口仍是 `add()`，但「更新」这一整段不存在了。

| 阶段 | 动作 | 关键参数 |
|---|---|---|
| 0 上下文 | 从 `messages` 表取本会话最近消息，供指代消解 | `limit=10` |
| 1 召回已有 | 新消息整体 embed，向量库直接检索已有记忆 | `top_k=10` |
| 2 抽取 | **一次** LLM 调用，输出 `{"memory":[{"id","text","linked_memory_ids"}]}` | `ADDITIVE_EXTRACTION_PROMPT` |
| 3 批量嵌入 | `embed_batch` 全部 text，失败逐条降级 | — |
| 4 CPU 加工 | 每条算 md5 hash、`text_lemmatized`（供 BM25）、时间戳 | — |
| 5 哈希去重 | 与召回集的 hash 集、批内 seen 集比对 | md5 精确匹配 |
| 6 批量落库 | 批量 insert，失败逐条 insert | — |
| 7 实体链接 | spaCy 抽实体 → 全局去重 → 批量 embed → 匹配或新建 → 合并 `linked_memory_ids` | 相似度 ≥0.95 视为同实体 |
| 8 存消息 | 写 `messages` 表并返回 | — |

三处必须记住的实现事实：

1. **输出 schema 里没有操作类型。** 没有 ADD/UPDATE/DELETE/NOOP 四选一，模型的动作空间被压成「抽出来 / 跳过」。UPDATE 与 DELETE 只存在于用户显式调用的 `update()` / `delete()` 里。
2. **prompt 的 Summary 与 Recently Extracted 两节在 OSS 路径是空的。** `generate_additive_extraction_prompt()` 支持这两个参数，`_add_to_vector_store` 调用时未传（默认 `None`）。实际有内容的只有：已有记忆（10 条）+ Last k（10 条）+ 新消息 + 观测日期 + 当前日期。
3. **`_should_use_agent_memory_extraction()` 是未被调用的死代码。** 实际 agent 判定是 `bool(agent_id) and not user_id`，决定是否追加 `AGENT_CONTEXT_SUFFIX`。

检索侧同样换了：`_search_vector_store()` 是语义 + BM25 + 实体三路加权，不是论文的单路向量检索。

$$\text{score}=\frac{s_{\text{semantic}}+s_{\text{bm25}}+s_{\text{entity}}}{\max_{\text{possible}}}$$

| 组件 | 实现 | 边界 |
|---|---|---|
| 候选池 | 语义检索 top-$\max(4k,60)$ | **只从语义来**；纯关键词命中进不了结果 |
| 语义阈值 | `threshold=0.1`，**融合前**卡原始语义分 | 语义不够，BM25/实体再高也救不回 |
| BM25 | qdrant `bm25` 稀疏向量（fastembed `Qdrant/bm25`），原始分经 sigmoid 归一 | 老 collection 无该 slot 时静默禁用 |
| BM25 参数 | 按查询词数五档：≤3 词 (5.0, 0.7)、≤6 (7.0, 0.6)、≤9 (9.0, 0.5)、≤15 (10.0, 0.5)、>15 (12.0, 0.5) | midpoint / steepness |
| 实体 boost | query 抽实体 ≤8 个 → 实体库 top_500、相似度 ≥0.5 → $\text{sim}\times0.5\times\frac{1}{1+0.001(n-1)^2}$ | $n$ = 该实体链接的记忆数 |
| 分母 | 1.0 / 1.5 / 2.0 / 2.5，取决于本次有哪些信号命中 | **同一分在不同查询下不可比** |
| 时间 | 无 recency、无 valid_time、无 MMR | `created_at` 只做展示与过期过滤 |

过期是**软过期**：`expiration_date` 存 payload，检索与 `get_all` 时过滤，`show_expired=True` 可见，数据不删。该字段只能由调用方传参设置——抽取 prompt 里没有任何要求模型推断有效期的指令，所以它不是自动遗忘机制，是手动 TTL。

存储三块：向量库（正文 + hash + lemmatized + 实体链接）、`history` 表（ADD/UPDATE/DELETE 全事件 + 旧值 + `is_deleted`）、`messages` 表（原始对话，按 `user_id|agent_id|run_id` 拼的 `session_scope` 索引）。

## 1.6 论文与 V3 的七处落差

| 论文 | V3 | 后果 |
|---|---|---|
| 更新阶段二次 LLM，四操作 tool call | **整段删除，只剩 ADD** | 每条消息从 1+n 次 LLM 降到 1 次 |
| `DELETE` 物理移除矛盾记忆 | 无；仅显式 `delete()` | 旧事实永久留存、仍可被检索 |
| `UPDATE` 比较信息量后替换 | 无；改写事实变成两条并列 | 知识更新靠检索排序碰运气 |
| 异步 summary $S$ | prompt 保留 `## Summary` 段但未传值 | 该节为空，跨会话查重失去全局视角 |
| （无） | md5 精确去重 | 只挡完全同文，近义重复照存 |
| 单路向量检索 | 语义 + BM25 + 实体 boost 融合 | 召回变强，分母浮动、候选仍受限于语义 |
| 时间戳交给答案模型换算 | 检索无时间项，靠答案 prompt 说"优先近的" | 矛盾消解从写时裁决降级为读时推测 |

一句话概括这次替换：**论文是「抽取 + 一致性维护」，V3 是「抽取 + 混合召回」。一致性维护被砍掉，换来写入 LLM 调用从 1+n 降到 1；补上的是 BM25、实体链接、哈希去重。**

成本账要分开算，不是单纯更便宜：

| 环节 | 论文 | V3 |
|---|---|---|
| 写入 LLM | 1 + n（n = 本轮事实数） | 1 |
| 写入 embedding | n 条记忆 | n 条记忆 + 1 批实体 + 1 批 BM25 稀疏 |
| 写入 CPU | 无 | spaCy 全量实体抽取 + 词形归一 |
| 查询 | 1 路向量检索 | 2 路检索 + ≤8 次实体库检索（并发 4）+ 融合打分 |

即：**推理成本下降，编码、存储与召回延迟上升**。代码确实更简单——没有中间态、没有回滚、没有操作序列。

## 1.7 冗余：来源、收敛与适用边界

ADD-only 会冗余，且冗余是设计出来的。三处主动放大：

1. **prompt 禁止「实体见过就跳过」**〔实现〕：明确要求「已知实体上的新事件必须独立抽出」，只为防漏抽。
2. **事实演化不覆盖旧值**：旧值 + 新值并列，靠 `linked_memory_ids` 记关系，不裁决有效性。
3. **跨会话查重近乎失效**：Phase 1 只召回 top-10 且是向量召回，`existing_hashes` 只覆盖这 10 条；summary 为空。于是「隔 50 轮、措辞差异大」的同一件事会被重写。

四个收敛约束，各自的盲区：

| 约束 | 挡什么 | 挡不住什么 |
|---|---|---|
| prompt 语义查重 | 明显等价的说法 | 措辞漂移的同义 |
| md5 精确 hash | 原句重抽、重复喂同一批消息 | 改一个字 |
| top-10 相似召回 | 近邻重复 | 距离远的重复 |
| 实体链接合并 | **实体**层面重复（同一 Max 只一个节点） | 记忆正文仍多条 |

注意最后一行的错位：**实体库收敛，记忆库发散**。冗余主要发生在记忆表，不在实体表。

这套方案仍被广泛采用，四个理由按重要性排：

1. **指标不惩罚冗余。** LoCoMo / LongMemEval / BEAM 判答案对错，不判存储是否精简。多存只稀释排序（top-200 下几乎看不见），漏存直接丢分。不对称惩罚使任何被这套指标驱动的实现都滑向多存。
2. **成本结构。** 冗余的边际成本是 embedding + 向量存储，单价低；省下的是每轮一次 LLM 决策。
3. **错在可恢复侧。** 误删/误覆盖不可逆且无感知；多存可事后 compaction、去重、靠排序压下。与事件溯源、LSM-tree、Git 同源：写入只追加，冲突消解推迟到读时或后台合并。
4. **读时可补救。** 检索返回 `created_at`，答案 prompt 明写「矛盾时优先 recent」。冗余在读侧可过滤——但正确性押在答案模型愿不愿看时间戳上。

四种场景下这套不成立：

| 场景 | 失效原因 |
|---|---|
| 高频更新事实（住址、职位、套餐） | 新旧同时被召回，答案五五开；无 valid_time 就没有「当前值」 |
| 严格上下文预算 | 每次塞 200 条，冗余变成 token 账单与延迟 |
| 有删除义务（合规、撤回） | 必须物理删并连带清实体链接 |
| 状态查询而非事件查询 | 「他现在住哪」需要唯一答案，多版本是毒药 |

业界收敛形态不是二选一，而是 **append-only 写入 + 定期 compaction**：写只追加（带 `created_at` / `supersedes`），读按时间或置信度消解，后台把同一 (主体, 谓词) 的旧版本折叠成「当前值 + 历史」并清理。V3 只做了第一步，第二步靠 prompt 兜，第三步没有——它是把一致性从写时挪到读时的中间态，不是终态。

## 1.8 评测集归属：harness 是自建的，数据集不是

`mem0` 主仓的 `evaluation/` 是 **git submodule**，指向 `mem0ai/memory-benchmarks`（克隆后为空目录，需单独拉）。该仓只有三个 benchmark：`locomo`、`longmemeval`、`beam`，数据集全部运行时从外部拉取，`datasets/` 被 gitignore。

| Benchmark | 数据集来源 | 谁构造的 |
|---|---|---|
| LoCoMo | ACL 2024，10 段对话 / ~1,540 计分题 | Maharana 等，外部 |
| LongMemEval | ICLR 2025，500 题 / 6 类 | Wu 等，外部 |
| BEAM | ICLR 2026，100 段对话 / 2,000 题 / 10 类能力 / 100K–10M | Tavakoli 等，外部 |

`benchmarks/beam/run.py` 头注释即写明 ICLR 2026，加载 `Mohammadta/BEAM` 与 `Mohammadta/BEAM-10M`；题目、rubric nuggets、10 类能力划分均为原 benchmark 自带，mem0 只改写 ingestion 与判分调用。

自建的是**协议层**：

- 统一三阶段 `Ingest → Search → Evaluate`，三个数据集共用一套 schema、checkpoint 与 UI；
- **top-k cutoff 扫描** `--top-k-cutoffs 10,20,50,200`，同一批检索结果在四个截断上重复判分；
- 答案生成 prompt（要求扫完所有记忆再答）、judge 口径（BEAM 的 rubric nugget 按 0/0.5/1 打分取均值，`pass_threshold=0.5`，event_ordering 另算 Kendall tau-b）；
- `--predict-only` / `--evaluate-only` / `--resume` 的工程壳。

所以对外报的 92.5%（LoCoMo top_200）这类数字，**数据集是别人的，口径是自己的**：top_200、gpt-5 判分、cat5 对抗题不计入——三者任一换掉，数就不是这个数。

<a id="c1-9"></a>

## 1.9 榜单现状：分数不可比的原因

2026 年这一批记忆系统分数，绝大多数是**厂商自跑自报**，且榜单归属方往往就是参赛方〔二手聚合站，未核原始 run 文件〕：

| 榜单 | 运营方 | 与参赛方关系 |
|---|---|---|
| AMB / Agent Memory Benchmark | Vectorize | 即 Hindsight 厂商 |
| OmniMemEval | MemTensor | 即 MemOS 厂商 |
| MemoryBench | Supermemory | harness，不发布榜单 |

三处硬伤，任何跨系统比较前必须先过：

1. **同一系统自报两个数。** ByteRover 发过 92.2 与 96.1；Zep 自报 LoCoMo 94.7，第三方复跑 75.1。差 20 个点不是模型差异能解释的。
2. **LoCoMo / LongMemEval 已饱和。** 头部 89–95，差距小于「换一个答案模型」的波动，这两个榜已无区分力。
3. **成本差异被隐藏。** Mem0 约 6,956 tokens/query，Hindsight 默认 23.9K–43.6K。同一分数在不同 token 预算下不是一件事。

有区分度的是 **BEAM 10M**（无窗口能装下）与 **PersonaMem / LifeBench**（偏好演化，前沿模型仍只有 50%–55%）。Mem0 在 BEAM-10M 上的弱项集中在 `event_ordering`（0.202）、`temporal_reasoning`（0.163）、`multi_session_reasoning`（0.261）——三项都需要跨条目重建结构，而 V3 是平坦 top-k。这不是实现 bug，是 §1.6 那笔取舍的必然结果。

<a id="c1-10"></a>

## 1.10 机制边界

- 压缩率 93.2%（$1-1764/26031$），端到端 p95 只降 91.6%——剩下的差值来自检索与生成两段与注入量无关的固定开销，不是纯 token 问题。
- 存储侧 Mem0 约 7k tokens/对话、Mem0ᵍ 约 14k，而 Zep 超过 600k〔正文〕。原文还提到 Zep 写入后立即检索常答错、数小时后重查才好转，说明其图构建是重异步管线——**这条对"能不能边聊边用"是决定性的**。
- 单跳领先、多跳一般，说明它擅长"一句话一个事实"，不擅长"两个事实拼一个答案"。指标 1 只测抽取，会把这类失败漏掉。
- 更新阶段只有 LLM 一次判断，没有置信度、没有二次确认、没有回滚。**它的错误是不可逆的单点错误**，不像 RAG 那样错在检索、下一次查询还有机会纠正。
